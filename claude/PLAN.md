# PLAN — selection head로 A-RAG baseline 개선 (PoC)

작성: Claude, 2026-11-10. 상태: **계획만. 아무것도 실행하지 않음.**
근거 코드: `jev_v2.2` = `jev_v2.1` 59e4dd8. 수치 출처는 `RESULTS.md`, `HANDOVER.md`, `experiments/fullft_grpo_20261103/`.

## 0. 목표와 판정

목표: A-RAG에서 **iteration↓ → 생성량↓ → 정확도↑**.

판정은 dev192(greedy)에서, 학습 안 한 native A-RAG(**N0**) 대비로 미리 고정함.

| 지표 | 통과 기준 |
|---|---|
| 정확도 (EM, F1) | N0 이상 (paired bootstrap으로 하락이 유의하지 않을 것) |
| 생성 토큰 | −20% 이상 |
| 도구 호출 | 감소. 목표 −10%. 단 아래 위험 1 참고 |
| 경보 | 2 iteration 동안 지표가 안 움직이거나, 빈 답·답 길이·KL이 급변 |

판정 iteration은 2로 고정. test320은 마지막에 한 번만 봄.

## 1. 먼저 알아야 할 사실 (이전 실험에서)

1. **생성 토큰의 약 45%가 청크 ID임.** 에피소드당 출력 약 102토큰 중 read_chunk ID 28.8 + support_ids 18.2 (B1 학습 전). 검색 인자 45.3, 답·문법 10.4.
   → 청크 선택을 head로 옮기면 학습 없이도 read_chunk ID 28.8토큰(−28%)이 사라짐. support_ids까지 코드가 채우면 −46%.
2. **모델은 과다 호출이 아니라 과소 수집 상태임.** 2~4hop 문제에 평균 2.4회 호출, 3·4hop에서 근거를 전부 확보한 문항 0~3%, 빈 답 36~41%, F1 약 19.
   → "호출 수를 깎아라"는 보상은 정확도와 충돌함. 이전 4개 arm이 호출을 못 줄인 이유.
3. 궤적 단위 보상은 결정의 51%에 신호 0을 줌. 단계별 근거 보상은 오프라인에서 11%로 줄임.
4. F1 부분 점수가 장황한 답을 키움 (B1 답 길이 3.1 → 7.7단어).
5. head 최대 확률 .92라 8 rollout이 거의 같음.

**그래서 이 PoC의 가설은 이렇게 잡음:** iteration은 "덜 부르기"가 아니라 "한 번에 맞는 청크를 읽기"로 줄인다. 생성량은 ID 토큰 제거로 구조적으로 줄인다. 정확도는 근거 라벨로 청크 선택과 멈춤을 직접 가르쳐 올린다.

## 2. 구조 (바꾸는 것은 read_chunk 경로 하나)

```
prefill 1회 → hidden
  ├ tool head: 0 keyword_search / 1 semantic_search / 2 read_chunk / 3 FINAL   (기존)
  ├ 0, 1 → 도구 prefix 공급 → LLM이 인자 생성                               (기존)
  ├ 2    → chunk head가 후보 중 선택 → 코드가 ID로 변환해 실행                 (신규, 생성 0토큰)
  └ 3    → LLM이 답 생성                                                       (기존)
```

**chunk head**
- 후보: 지금까지 검색 결과로 본 청크 중 아직 안 읽은 것 (K개, 가변). 이미 읽은 청크는 마스크.
- 후보 표현 e_i: 같은 prefill의 hidden에서, 그 청크가 tool 메시지에 나온 구간의 평균. 상태 h: 마지막 토큰 hidden.
- 점수: `s_i = (W_q h)·(W_c e_i)` (64차원), STOP 점수 `s_stop = w·h`. 후보 수가 바뀌어도 같은 가중치.
- 선택: 고른 후보를 빼 가며 반복, STOP에서 종료. 최소 1개, 최대 8개. log π는 각 선택 확률의 합 (정확히 계산됨).
- 추가 LLM forward 없음.

**결정 필요 (D1):** FINAL의 `support_ids`도 LLM이 쓰지 않고 "읽은 청크"로 코드가 채울지. 채우면 −18토큰이 더 빠지지만 답 형식이 baseline과 달라짐. 기본안: head arm에서만 채우고, 토큰 수는 두 방식 모두 보고.

## 3. 단계

각 단계는 smoke → 본 실행 순서. smoke가 통과 기준을 못 넘으면 본 실행을 하지 않음.

### S0. 환경 + baseline 재현 + 여유 측정 (학습 없음, 약 1시간)
- venv 복원, `pytest tests` 18개 통과.
- smoke: N0 greedy 8문항. 오류 0.
- 본 실행: N0 greedy dev192. 기대값 F1 19.3 / 호출 2.48 / 출력 107.8 (A1 학습 전). ±1문항 수준으로 맞아야 함.
- 여유 측정 (N0 궤적 + train의 근거 표시, 신규 스크립트 1개):
  - 호출 분류: 새 근거를 찾거나 읽은 호출 / 낭비 호출 (근거 아닌 청크 읽기, 같은 검색 반복)
  - read_chunk로 고른 ID 중 근거 비율 (text 선택의 정확도. S1의 비교 기준)
  - FINAL 시점 근거 확보율
- **판단:** 낭비 호출이 전체의 10% 미만이면 "호출 −10%"는 목표에서 빼고 "정답당 호출 수"로 바꿈.

### S1. 라벨 생성 → head KD (약 2시간, GPU는 수집 때만)
- 수집: train576에서 N0를 문항당 greedy 1 + 샘플 2회 실행. 결정 시점마다 h, 후보별 e_i, LLM이 실제로 한 선택을 저장.
- 라벨 (train의 근거 표시로 오프라인 계산, 평가 데이터에는 쓰지 않음):

| 상태 | tool 라벨 | chunk 라벨 |
|---|---|---|
| 후보에 안 읽은 근거가 있음 | read_chunk | 그 근거들, 이후 STOP |
| 근거를 전부 읽음 | FINAL | – |
| 그 외 | 검색 (keyword/semantic 중 LLM이 고른 쪽. LLM이 검색을 안 골랐으면 두 검색 logit의 합에만 손실) | – |

- 학습: tool head(기존 MLP, 전체 층)와 chunk head를 저장한 feature로 학습. LLM 고정. 문항 단위로 80/20 나눠 검증.
- smoke: 16문항으로 수집 → 라벨 분포 출력 → 1 epoch. 확인: 후보 구간을 못 찾는 경우 0, 세 라벨이 모두 존재, 손실 감소.
- **통과 기준:** 검증 상태에서 chunk head가 고른 청크의 근거 비율 ≥ S0에서 잰 text 선택의 근거 비율. tool 정확도는 "LLM 선택과 일치율"과 "라벨 일치율"을 둘 다 보고.

### S2. head 붙인 모델 평가 = H0 (학습 없음, 약 20분)
- smoke 8문항: 오류 0, read_chunk 생성 토큰 0, 실행된 ID가 전부 후보 안.
- 본 실행: dev192 greedy.
- **통과 기준:** 생성 토큰 −20% 이상, 정확도 N0 이상.
- 정확도가 떨어지면: head가 만든 궤적으로 S1을 1회 더 돌림 (상태 분포가 달라진 것을 보정). 그래도 떨어지면 GRPO로 가지 않고 보고.

### S3. 보상 오프라인 검증 (GPU 없음, 30분)
S1·S2에서 모은 궤적에 보상식을 적용해 실행 전에 확인.

- 최종 보상: `R = acc · 0.8^호출 · 0.995^생성토큰`, `acc = 0.5·EM + 0.5·F1`, 답 60자 상한. (곱셈이라 오답은 길이와 무관하게 0 → 짧은 오답이 긴 정답을 못 이김.)
- 단계 보상: 호출마다 `0.5 · (새로 찾거나 읽은 근거 수 / 근거 수) − 0.05`. 마지막 결정에 R.
- advantage: 결정 i의 return-to-go − 같은 문항 8개 궤적의 같은 단계 평균. 표준편차로 나누지 않음.
- **통과 기준:** 신호 0인 결정 < 20%. 보상과 답 길이의 상관 ≤ 0. 정답 궤적 중 호출이 적은 쪽의 보상이 더 높음. 미달이면 계수를 고치고 다시 검증.

### S4. GRPO 2개 (각 약 3.5시간, 순차)

| | H1 (2차) | N1 (3차, 대조군) |
|---|---|---|
| 시작 | 원본 LLM + S1 head | 원본 LLM |
| 학습 | LLM 전체 + head 전체 | LLM 전체 |
| 결정 | tool head, chunk head | 도구명·청크 ID 토큰 |

- 공통: 같은 문항, 문항당 8 rollout, 192문항 × 2 iteration, 같은 보상식, 같은 lr 1e-6, KL β .02, seed 동일. 결정 i에 속한 모든 것(head logp, 그 단계의 생성 토큰)에 같은 A_i를 씀.
- H1에서 바꿔야 하는 코드: 지금은 저장한 feature로 head 손실을 계산해 LLM까지 기울기가 안 감. replay forward의 hidden에서 feature를 다시 뽑아 head 손실을 계산하도록 변경.
- 탐색: head 샘플링 온도를 올려, 행동 순서가 다른 그룹이 50% 이상 되게 맞춤 (native는 기존 T=4 보정과 같은 방식).
- 평가·저장: iteration 0, 1, 2에서 dev192 평가, iteration마다 LLM 가중치 저장.
- smoke (16문항 × 8 × 1 iteration, 업데이트 2회): 다시 계산한 head logp와 rollout 때 값의 차이 < 0.05, 토큰 replay 차이 < 0.05, 신호 있는 그룹 ≥ 50%, KL 유한, GPU 최대 메모리 기록, 오류 0.
- GPU 약 70GB 필요. 다른 프로젝트 작업은 건드리지 않음.

## 4. 결과 표 (미리 고정)

dev192, greedy. N0/H0는 학습 전, N1/H1은 iteration 2.

| 조건 | EM | F1 | 도구 호출 | 생성 토큰 | 그중 ID 토큰 | 지연 proxy | 빈 답 | 답 길이 |
|---|---|---|---|---|---|---|---|---|
| N0 native | | | | | | | | |
| H0 head (KD) | | | | | | | | |
| N1 native + GRPO | | | | | | | | |
| H1 head + GRPO | | | | | | | | |

보조 표 2개: hop별(2/3/4), 청크 선택 품질(고른 청크 중 근거 비율, 근거 확보율).

읽는 순서:
1. H0 vs N0 → 구조만의 효과 (토큰 감소, 선택 정확도).
2. H1 vs H0, N1 vs N0 → 각자 GRPO가 준 변화.
3. H1 vs N1 → 같은 학습 예산에서 head의 효과. **이것이 주 결론.**
4. 비용이 줄었으면 반드시 확인: 정답을 유지한 문항에서 줄었는가, 빈 답·조기 종료가 늘어서 줄었는가.

## 5. 위험

1. **iteration이 안 줄 수 있음.** 근거가 부족한 상태라 정확도를 올리면 호출이 늘 수 있음. S0의 낭비 호출 측정으로 먼저 판단.
2. **근거 라벨 정책이 baseline보다 호출을 늘릴 수 있음.** "근거 다 읽을 때까지 검색" 라벨이기 때문. S2에서 호출 수가 N0보다 20% 넘게 늘면 FINAL 라벨 기준을 완화.
3. **constrained decoding 대비 이점이 작을 수 있음.** N0·N1은 이미 ID를 후보로 제한해 생성함. 그래서 head의 이점은 "없는 ID 방지"가 아니라 토큰 0·직접 지도·단계별 신호로만 주장 가능.
4. seed 1개, dev192는 1문항 = 0.5%p. 작은 차이는 판정 불가로 보고.
