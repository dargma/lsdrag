# 멀티모달 A-RAG와 EmbeddingGemma 2 비교 실험 실행 지시서

## 목적과 완료 조건

텍스트로 검색하고 VLM으로 근거를 읽는 A-RAG를 기준으로, EmbeddingGemma 2의 텍스트 질의→이미지 검색과 이에 적합한 에이전트 인터페이스가 정답 근거 확보 및 답변 정확도를 개선하는지 검증한다. 모델 설치나 데모 구현에서 끝내지 않고, 고정된 이미지 관련 M3DocVQA 질문 50개에 대한 B0·V1·V2·C1 평가와 근거를 갖춘 최종 보고서까지 완료한다.

핵심 가설은 문서 탐색 자체보다 **문서 내부의 정답 그림 선택**, 특히 캡션에 없는 시각적 속성을 묻는 질문에서 개선이 나타난다는 것이다. 결과가 개선되지 않아도 동일한 평가 절차와 실패 분석으로 보고한다.

완료 조건은 네 실험의 실행 기록, 질문별 예측·근거 전달 기록, 평가 지표, 짝지은 통계 비교, 대표 성공·실패 사례, 실행 가능한 코드와 고정 설정, 최종 보고서의 Git 저장 및 push이다. 실행 불가능한 구성요소나 누락된 근거 정답을 임의 대체하여 완료로 표시하지 않는다.

## 최신 사용자 결정과 판단 권한

- 최종 질문 수는 전체 dev 2,441개 대신 **이미지 근거와 관련성이 높은 50개**로 제한한다. 원 계획에 적힌 데이터 규모는 수집 시 실제 파일 수와 메타데이터로 확인한다.
- 개발용 질문은 최종 50개와 분리한다. 최종 질문의 정답이나 성능을 보고 프롬프트·검색 설정을 수정하지 않는다.
- V2에서는 멀티모달 임베더의 잠재력을 활용하기 위해 A-RAG 도구, 프롬프트 및 탐색 흐름을 재구성할 수 있다.
- rerank는 A-RAG 기본값에 맞춰 사용하지 않는다. 확인한 원본 커밋은 `a44de6b2216bf6791979c4b6ac4ae106212fa1a6`이며 설정과 소스에서 rerank가 발견되지 않았다.
- Reader는 우선 Gemma 4 26B-A4B instruct를 사용한다. 자원·속도에 따라 더 작은 VLM을 선택할 수 있으며 선정 근거와 실제 모델 버전을 기록한다. 네 실험에는 같은 Reader를 사용한다. 본 평가 도중 변경하면 비교 대상 전체를 다시 실행한다.
- 추가 질문 없이 수행자가 판단하고 기록하며 진행한다. 기존 계획의 rerank·렌더링 시점·전체 실행 전 승인 항목은 추가 승인 대신 결정 기록과 사전 소요 시간 보고로 대체한다.
- 모델 접근 권한, 네트워크 또는 자원 부족으로 불가능한 작업은 정확히 기록한다. 결과나 실행 성공을 만들어내지 않는다.

## 실험 조건과 해석

| 실험 | 텍스트 검색 | 이미지 검색 | 도구와 프롬프트 | 비교 목적 |
|---|---|---|---|---|
| B0 | Qwen3-Embedding-4B | 없음 | A-RAG에 그림 연결과 VLM 전달만 추가 | 텍스트 검색 기반 멀티모달 기준 |
| V1 | B0와 동일 | EmbeddingGemma 2 그림 임베딩, 순위 융합 | B0와 동일 | 이미지 검색 경로 추가 효과 |
| V2 | B0와 동일 | V1을 유지하고 명시적 시각 검색 제공 | 시각 근거 탐색에 맞게 재구성 | 도구·프롬프트를 포함한 인터페이스 개선 효과 |
| C1 | EmbeddingGemma 2 텍스트 임베딩 | 없음 | B0와 동일 | 텍스트 임베더 교체 효과 |

B0에서도 그림 캡션 청크를 읽으면 연결 이미지를 전달한다. C1 역시 같은 연결을 유지한다. 따라서 C1의 '이미지 경로 없음'은 이미지 **검색** 경로가 없다는 뜻이며 Reader의 이미지 해석을 제거하지 않는다.

V1의 이미지 검색 결과는 동일한 그림에 연결된 캡션 또는 주변 문맥 청크 ID로 변환한다. B0와 같은 결과 스키마·읽기 도구로 그림을 열 수 있어야 하며, V1만의 도구 지침을 추가하지 않는다. 동일 청크가 여러 채널에서 나와도 중복 후보로 취급하지 않는다.

V2는 도구와 프롬프트를 함께 개선하는 묶음 실험이다. V2−V1 차이만으로 개별 프롬프트 문구나 단일 도구의 인과 효과를 주장하지 않는다. 추가 분해 실험은 필수 네 실험이 완료된 뒤 자원이 허용할 때 실시한다.

모든 조건에서 질문 집합, 문서 코퍼스, 파싱 산출물, 청크 경계, Reader, temperature 0, 최대 루프·출력·컨텍스트 예산, 이미지 전달 예산을 동일하게 유지한다. 원본 A-RAG를 재현하는 text-only 설정도 제공하되 필수 비교표의 B0와 구분한다.

사용자 원안의 모델 크기·차원·입력 제한·이미지 토큰 수는 모델 카드와 최소 실행으로 확인한 후 실행 설정에 확정한다. 확인되지 않은 값을 검증된 사양으로 기록하지 않는다. 임베더는 임의 대체하거나 차원을 축소하지 않는다.

각 모델과 데이터는 revision 또는 파일 해시, 패키지는 버전 잠금, 프롬프트는 Git 해시로 추적한다. 문서 링크만 확보한 상태와 실제 실행이 통과한 상태를 구분한다.

## 데이터 선택과 근거 정답

### 최종 평가 질문 50개

1. MultimodalQA/M3DocVQA dev 메타데이터에서 이미지가 정답 추론에 필요한 근거로 명시된 질문을 후보로 삼는다. 단순히 문서에 그림이 있다는 이유로 포함하지 않는다.
2. 질문 ID를 정렬하고 고정 시드 `20261013`으로 추출한다. 이미지 단독, 이미지+텍스트, 이미지+표 등 실제 존재하는 근거 조합과 질문 유형을 층화한다. 층별 후보 수·선택 수와 선택 알고리즘을 저장한다.
3. 개발용 50개를 먼저 분리하고 최종 50개를 선정한다. 후보가 부족하면 개발 집합을 줄이고 그 사유를 기록한다. 최종 질문 수를 맞추기 위해 비이미지 질문을 조용히 섞지 않는다.
4. 성능과 무관하게 판정할 수 있는 데이터 품질 기준을 사전에 적용한다. 수집 실패, 손상 PDF, 사라진 근거에 대한 제외 기준과 대체 후보 순서를 실행 전에 고정한다. 제외 전후 모집단과 실패 수를 공개한다.
5. 고정 manifest에 질문 ID, 원문, 답의 원본 형식, 근거 ID, 근거 모달리티, 층, 선택 사유를 저장하고 해시를 남긴다. 에이전트 실행 입력에는 질문과 검색 코퍼스만 제공하고 정답·근거 라벨은 평가기에만 제공한다.

개발 질문과 최종 질문은 최소한 ID가 겹치지 않아야 한다. 가능하면 근거 문서도 분리하고 문서 공유율을 기록한다. 개발 집합으로 설정을 고정한 뒤 최종 평가를 한 번 실행한다. 오류 수정 재실행은 수정 이유와 영향받은 실험 전체의 새 결과를 남긴다.

### 검색 코퍼스

질문을 50개로 줄이는 것과 검색 대상 문서를 정답 문서만으로 줄이는 것은 다르다. 최종 평가는 가능하면 원 벤치마크의 접근 가능한 전체 PDF 코퍼스를 사용한다. 개발 단계는 근거 문서와 고정 추출한 무관 문서로 시작한다.

전체 코퍼스가 자원상 불가능하면 정답 문서와 충분한 고정 distractor 문서로 제한하고, 그 규모·추출법을 보고한다. 이 경우 원래 오픈 도메인 전체 코퍼스와 동일한 난도라고 주장하지 않는다. 모든 실험에는 동일 코퍼스 manifest를 적용한다.

### 페이지와 그림 정답 매핑

원 메타데이터가 문서·원본 이미지 ID만 제공할 수 있으므로 PDF 페이지 번호나 MinerU 그림 ID가 직접 주어진다고 가정하지 않는다. 원본 이미지 URL/ID/파일과 PDF 렌더링·파싱 그림 사이의 대응을 별도로 구축한다. 매칭 방법, 좌표, 확신도, 수동 검증 여부를 기록한다.

정답 페이지·그림을 신뢰성 있게 연결하지 못한 경우 해당 세부 지표는 미확인으로 둔다. '매핑 가능한 질문에서의 성능'과 매핑 커버리지를 함께 보고하며, 매핑 불가를 검색 실패나 정답 그림 발견으로 바꾸지 않는다. 이미지 정답 매핑은 시스템 출력에 영향을 받지 않도록 고정한다.

위키 렌더링 시점 차이는 수집 시각·URL·PDF 해시와 함께 기록한다. 정답 문자열 부재는 이상 탐지 신호로 사용하되 이미지 질문의 근거 소실을 곧바로 의미하지 않는다. 의심 사례는 원본 이미지·페이지를 확인하고 유지·제외·불확실 결정을 사유와 함께 남긴다.

## 파싱과 검색 인터페이스

MinerU의 공식 저장 API/명령으로 결과를 보존하고 [출력 형식](https://opendatalab.github.io/MinerU/reference/output_files/)과 실제 산출물을 대조한다. 이미지 파일 경로는 출력의 참조를 해석하며 파일명 규칙으로 추측하지 않는다.

공통 IR에는 `document_id`, `page_index`, `chunk_id`, `kind`, `text`, `figure_id`, `image_path`, `bbox`, `source_ref`를 상황에 맞게 보존한다. 문서 ID는 안정적인 원본 식별자에 연결하고 페이지 번호의 0/1 기준을 명시한다. 이미지·캡션·표의 연결은 여러 대 여러 관계도 표현할 수 있어야 한다.

청크 크기, 표 분할, 페이지 경계 결합은 개발 샘플로 결정한다. 표는 헤더와 원래 셀 관계를 유지하고 과도한 분할을 피한다. 캡션 없는 그림은 원문 주변 문맥을 사용하되 '캡션 없음'을 표시한다. 합성 캡션을 도입하면 검색 조건이 바뀌므로 필수 실험에는 공통 사전 처리로 확정하기 전 적용하지 않는다. 캡션 없는 그림 비율과 문맥 연결 실패율을 기록한다.

인포박스, 그림·캡션 연결, 잘린 문단·표, 여러 그림이 합쳐진 영역을 실제 페이지와 대조한다. 오류 샘플과 수정 규칙을 저장하고 네 실험에서 같은 수정본을 사용한다.

검색 도구는 ID, 종류, 짧은 스니펫, 문서·페이지 정보만 반환한다. 이미지 바이트는 읽기/열람 요청 뒤에만 전달한다. 텍스트·이미지의 전달 집합을 분리해 중복 방지하고 잘못된 ID·빈 검색·깨진 파일은 구조화된 오류로 알린다.

V1은 텍스트·이미지 원점수를 더하지 않는다. RRF 등 순위 기반 융합을 사용하고 상수와 채널 후보 수를 개발 단계에서 확정한다. Qwen 쿼리 지시문은 쿼리에만 적용하고 EmbeddingGemma 접두어는 모델 카드와 실제 API에 맞춰 query/document/image별로 저장한다.

### V2 설계 방향

- `image_search`: 텍스트 질문으로 그림을 검색하고, 필요하면 이미 발견한 문서·페이지 범위로 제한한다. 범위는 에이전트가 발견한 ID만 사용하며 정답 메타데이터를 주입하지 않는다.
- `figure_read`: 그림과 인접 캡션·문맥을 명시적으로 열람한다. 고해상도 입력·확대가 필요하면 고정된 전달 예산 안에서 선택한다.
- 텍스트 탐색으로 엔티티·후보 문서를 확인한 뒤 시각 질문으로 재질의하거나, 처음부터 시각 검색을 사용하는 경로를 모두 허용한다.
- 외형·색·배치·그래프·도표 질문은 캡션만으로 결론내리지 않고 이미지를 확인하도록 안내한다. 근거가 부족하면 질의를 바꾸거나 다른 후보를 읽고, 없는 근거를 추정하지 않도록 한다.
- 원본 A-RAG의 자율적 반복 탐색, 점진적 정보 공개, 중복 방지는 유지한다. 도구 설명과 프롬프트 변경본·변경 이유를 버전 관리한다.

페이지 전체 임베딩, 이미지+캡션 결합 임베딩, 후보 재순위화는 별도 확장 실험이다. 필수 비교에 조용히 추가하지 않는다.

| 0 계획 고정 | 사용자 최신 결정 반영, 원본 코드 점검 | 본 지시서, 결정 기록 | 비교 조건과 평가 범위 명확화 |

| 7 본 평가 | 고정 50개에 네 실험 실행, 재개 가능한 저장 | 질문별 예측·trace·오류·비용 | 모든 질문의 성공/실패 상태와 평가 결과 확보 |
| 8 비교 보고 | 통계, 근거 회수, 사례 검토 | 최종 보고서·지표·도표 | 결과 출처 추적 가능, Git push 및 백업 확인 |

1단계에서 vLLM의 도구 호출, tool-role 이미지 수용 여부, 실제 VLM의 이미지 인식을 각각 시험한다. API가 메시지를 수락했다는 것만으로 이미지 인식 성공을 간주하지 않는다. 필요하면 tool 응답 직후 user-role 이미지 메시지에 도구 ID와 근거 ID를 연결하는 공통 어댑터를 사용한다.

환경은 파서·임베더·Reader 사이 의존성 충돌을 피하도록 가상환경을 분리한다. 무관한 실행 프로세스는 종료하지 않는다. 원래 Reader가 자원에 맞지 않으면 지원되는 작은 Reader를 개발 집합에서 고르고 본 평가 전에 고정한다.

각 단계 종료 시 수행 내용, 확인된 사실, 불확실성, 다음 작업을 짧게 보고한다. 장기 실행 전에는 처리량 측정에 따른 예상 시간·공간을 기록하고 현재 코드를 커밋한다.

## 평가와 로그 명세

### 정답 정확도

- M3DocVQA 논문·공개 평가 코드의 원래 지표를 확인해 동일 정규화와 다중 정답 처리를 적용한다. 지표 이름만 비슷한 임의 구현으로 대체하지 않는다.
- A-RAG의 LLM 판정 정확도와 포함 일치 정확도를 함께 계산한다. 판정 프롬프트·모델·설정·원문 응답을 보존한다.
- 기본 판정기는 Reader와 같은 서버를 사용하되 평가 세션은 분리하고 실험 이름은 가린다. 판정 실패는 정답/오답으로 조용히 치환하지 않는다. 불일치 사례를 검토하고 판정 오류 수를 기록한다.

### 검색과 이미지 전달

검색 후보에 등장한 근거, 에이전트가 실제 읽은 근거, VLM 요청에 실제 포함된 이미지의 세 단계를 각각 기록한다. 문서·페이지·그림 단위로 gold evidence recall과 '하나 이상 확보'·'필요 근거 모두 확보' 비율을 계산한다. 여러 근거가 필요한 질문에서 하나를 찾은 것만으로 완전 성공으로 처리하지 않는다.

주 관심 지표는 **이미지 관련 질문의 정답 정확도**, **정답 그림 열람률**, **정답 그림의 실제 VLM 전달률**이다. 페이지·그림 지표에는 매핑 가능한 분모와 커버리지를 명시한다. 문서 발견에는 성공했으나 그림 선택에 실패한 비율을 별도로 분석한다.

### 집계와 비용

이미지 단독·이미지+텍스트·이미지+표 등 실제 근거 조합, 질문 유형, 캡션 유무, 시각 속성 여부로 분해한다. 이 50개 평가만으로 일반 텍스트·표 질문에서의 성능 유지나 M3DocVQA 전체 성능을 주장하지 않는다. 별도 텍스트·표 진단 집합을 평가했다면 보조 결과로 구분한다.

질문별 루프 수, 도구 호출 수, 검색 스니펫 토큰, 읽은 텍스트 토큰, 이미지 수·중복 억제 수, 서버가 보고한 입력/출력 토큰, 지연 시간, 오류·재시도 횟수를 저장한다. 이미지 토큰을 서버가 제공하지 않으면 추정치와 실측치를 구분한다. 인덱싱·파싱의 일회성 비용과 질문당 추론 비용을 분리한다.

### 짝지은 비교와 실패 분석

동일 질문 ID로 B0 대비 V1·V2·C1과 V1 대비 V2의 정확도 차이, 이긴/진 사례 수를 계산한다. 주 비교는 V2−B0로 사전 지정한다. 질문 단위 paired bootstrap 95% 신뢰구간과 이진 정답에 대한 exact McNemar 검정을 사용하며, 부차 비교의 다중 검정 여부를 명시한다. 질문이 근거 문서를 공유하면 그 의존성과 표본 크기 한계를 기록하고 가능한 경우 문서 단위 민감도 분석을 추가한다.

50개가 작은 차이까지 검출하기에 충분하다고 사전 단정하지 않는다. 효과 크기와 신뢰구간으로 결론 강도를 결정한다. 개발 집합 수치는 최종 평가 근거로 합산하지 않는다.

실패는 (1) 근거 미발견, (2) 후보를 찾았으나 열람/이미지 전달 실패, (3) 정답 이미지를 전달했으나 오답, (4) 판정 오류로 분류한다. 데이터 손상·근거 소실·매핑 불가·서버 오류는 별도 상태로 보존한다. 모달리티별 B0 오답→개선안 정답 및 반대 사례를 수와 대표 근거로 제시한다.

외부 기준으로 [M3DocRAG 논문](https://arxiv.org/abs/2411.04952)의 ColPali + Qwen2-VL 7B 보고 수치를 출처·설정과 함께 싣는다. 질문 선택, 코퍼스, 위키 렌더링 시점, Reader가 달라 본 실험과 직접적인 우열 검정 대상이 아님을 표시한다.

## 저장소와 자원 운영

코드 작업과 데이터 처리는 `/content/local_fast/lsdrag-work/`에서 실행한다. PDF, 파싱 결과, 이미지, 모델, 인덱스, 추론 중간 결과는 로컬 고속 디스크에 둔다. Drive는 백업 대상으로만 사용하며 파싱·추론·인덱싱에서 읽지 않는다.

Git에는 코드·설정·프롬프트·manifest와 해시·소규모 지표·보고서를 넣는다. 대용량 데이터, 모델, 인덱스, 인증정보는 제외한다. 백업은 스냅샷을 백그라운드로 복사하고 완료 상태·실패 파일·재시도를 기록한다. 복사되지 않은 파일을 백업 완료로 표시하지 않는다.

GPU 작업은 파싱→임베딩→Reader 평가 순으로 배치하는 것을 기본으로 하며, 모델을 순차 해제해 메모리를 관리한다. 가중치 용량과 디스크 여유를 먼저 확인한다. 필요하면 재다운로드 가능한 이번 작업 캐시만 정리하고 다른 프로젝트의 파일·프로세스는 건드리지 않는다.

| 경로 | 역할 |
|---|---|
| `docs/EXPERIMENT_PLAN.md` | 실행 지시서 |
| `docs/DECISIONS.md` | 설정·모델·데이터 판단 근거 |
| `configs/`, `prompts/` | 실험별 고정 조건 |
| `src/`, `scripts/`, `tests/` | 실행·평가·검증 코드 |
| `lab/CURRENT_STATE.json` | 단계 상태·경로·실행 ID |
| `lab/RESEARCH_JOURNAL.md` | 확인 사항과 진행 기록 |
| `lab/registry/` | 실험 설정·소규모 결과·manifest |
| `lab/reports/` | 사전 확인 및 최종 비교 보고서 |

환경 사전 확인, 개발 파싱·인덱싱, B0 개발 확인, B0 본 평가, V1·V2·C1 각각의 구현 및 평가, 최종 보고서 완료 시 commit 후 push한다. 장기 실행 전에도 커밋한다. push 실패는 기록하고 다음 커밋 때 재시도하며 로컬 작업을 계속한다.

## 최종 보고서 구성

1. 평가 범위와 핵심 결론: 이미지 관련 고정 50개에서 무엇이 개선되었는가.
2. 모델·패키지·소스 버전, 모든 실험 설정, 변경된 도구·프롬프트.
3. 질문 선정, 코퍼스 규모, 수집 실패, 렌더링 시점 영향, 근거 매핑 커버리지.
4. 정확도·그림 열람/전달률·문서/페이지 recall·비용 비교표와 신뢰구간.
5. 근거 조합별 분해, 승패 쌍, 주요 실패 패턴과 대표 그림·trace.
6. 이미지 검색 자체와 에이전트 인터페이스 변경의 효과 구분, 텍스트 임베더 통제 결과.
7. 외부 기준과 비교 한계, 검증하지 못한 범위, 다음 실험 제안.
8. 재현 명령, 코드/설정/입력 해시, 결과 경로, 백업 상태.


## 2026-10-13 추가 확정: Mem-Gallery 보조 평가

사용자가 보조 대화에서 M3DocVQA 본 평가를 이미지 관련 50문항으로 축소하고 Mem-Gallery 보조 50문항 추가안을 승인했다. 기존 200개 후보 manifest는 과거 선정 산출물이며, 본 평가 전에 개발 집합과 분리된 50개 manifest를 고정 시드·근거 유형 층화로 새로 생성하고 해시를 기록한다. 모델 성능을 보고 문항을 고르지 않는다. 이미 수집한 문서와 실행 중인 개발 작업은 재사용한다.

Mem-Gallery는 Visual-centric Search 25개와 Visual-centric Reasoning 25개를 선정한다. 공식 데이터 JSON과 평가 코드를 먼저 확인하고, 질문 이미지 유무·근거 대화·정답 이미지 참조와 시간 범위를 검증한다. 문항 수가 부족한 경우 중복하거나 다른 유형을 조용히 섞지 말고 가능한 수와 사유를 보고한다. 공식 자료: https://github.com/YuanchenBei/Mem-Gallery 및 https://arxiv.org/abs/2601.03515.

- 해당 시나리오에서 질문 시점에 접근 가능한 대화 전체와 연결 이미지를 검색 대상으로 사용한다. 세션·날짜·대화 순서·이미지 연결을 보존하고 정답 근거만으로 코퍼스를 구성하지 않는다.
- B0는 대화 텍스트와 제공 캡션으로 검색하고 읽을 때 연결 이미지를 전달한다. V1은 이미지 임베딩 검색과 RRF를 추가한다. V2는 명시적인 이미지 검색·열람과 앞뒤 대화 확인을 제공한다. 보조 평가 필수 비교는 B0/V1/V2이며 C1은 M3DocVQA 본 평가에서 유지한다.
- 같은 Reader, 디코딩, 질문, 코퍼스, 이미지·루프 예산을 고정한다. 질문 이미지가 있으면 모든 조건의 Reader에 같은 입력을 제공하고 질문 이미지 유무별로 집계한다. 질문 이미지의 직접 검색 활용은 별도 확장으로 분리해 이미지 인덱스 추가 효과와 혼동하지 않는다.
- 정답 근거 대화와 이미지를 직접 제공하는 Reader 진단을 별도로 실행한다. 이 조건의 결과를 검색 시스템 점수에 합산하지 않는다.
- 공식 정답 지표와 정답 이미지 검색·전달률, 근거 대화 회수율, 비용을 보고한다. 같은 대화에서 나온 질문의 의존성을 고려해 대화 단위 bootstrap 민감도 분석을 함께 제시한다.
- M3DocVQA 50문항과 Mem-Gallery 50문항 결과는 별도 표로 보고한다. 보조 평가로 장기 기억 전반의 성능이나 전체 벤치마크 우위를 주장하지 않는다.

실행 순서는 현재 개발 파싱·B0 파일럿 완료 → M3DocVQA 50문항 선정 및 네 조건 평가 → Mem-Gallery 보조 평가 → 통합 비교 보고서다. 추가 승인 없이 단계별 검증과 자원 확인을 거쳐 진행하고, 실패는 원인과 재시도 기록을 보존한다. 이 절은 실행 범위의 변경이며 해당 평가가 완료되었다는 뜻이 아니다.

최신 범위 변경: 사용자가 두 벤치마크 모두 최종 평가 50문항으로 축소했다. 이는 이전 M3DocVQA 100문항·Mem-Gallery 60문항 결정을 대체한다. 개발 집합은 최종 평가와 계속 분리하며, 기존 수집·파싱 결과를 재사용한다. 본 평가 전에 각 50문항의 실제 입력 manifest와 해시를 확정한다.
