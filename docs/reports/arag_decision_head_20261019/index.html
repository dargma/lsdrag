A-RAG decision head 실험

도구 선택을 분류로 바꾸고, 인자 생성은 같은 LLM에 맡기면?

Qwen3-4B · MuSiQue 2-hop100문항 paired 평가
배경방법실행 흐름Tool call결과Raw 사례시사점부록
결과 요약. 답변 F1 31.11→31.57%, 평균 시간 1.337→0.978초(26.8% 감소)를 관측했다. 품질 향상은 미입증이며 공유 GPU 측정이다. Read 인자 선택은 품질 손실로 채택하지 않았다.
BACKGROUND

1. 배경

출발점은 Jev 같은 decision 모델의 아이디어였다. “도구를 고르는 데 필요한 텍스트 생성을 작은 분류 head로 바꾸면, A-RAG의 정확도를 유지하면서 빨라질까?” 이를 검색·읽기·종료를 반복하는 텍스트 QA에서 확인했다.

비교군 Native는 같은 Qwen reader가 도구 이름·인자·답변을 직접 생성하는 이 저장소의 A-RAG 방식 구현이다. Jev 모델을 사용한 실험이나 공식 A-RAG 전체 벤치마크 재현은 아니다. A-RAG 원 논문 · TypeSafe

METHOD

2. 실험 방법

항목설정
ReaderQwen3-4B-Instruct-2507 · frozen · BF16 · greedy · non-thinking
데이터MuSiQue-Ans v1.0, answerable 2-hop. 질문별 제공 문단 안에서 검색.
학습 / 검증teacher 32문항 → train24(82상태) / validation8(29상태).
주 평가미사용 dev100 × Native/Head = 200 episode. 모델·head 고정, 문항별 실행 순서 교대.
검색 / GPUembeddinggemma-2(768차원) · RTX PRO 6000 Blackwell 약 96GB, 공유 환경.
실행 한도최대 8 tool calls + FINAL · context 16,384 · 출력 512 tokens.

학습한 것은 무엇인가?

teacher는 같은 reader의 Native 경로다. 각 결정 직전의 마지막 hidden(2560차원)에 4-way linear action head를 붙여 teacher의 행동을 모방했다. 종료는 별도 head가 아니라 FINAL class다. backbone은 고정하고 작은 head만 학습했다.

정답 trajectory만 골라 학습한 것은 아니다. train24 중 teacher가 EM 정답을 낸 것은 5문항이다. 따라서 현재 학습 목표는 최적 행동이나 최종 정답률이 아니라 teacher 행동 일치다. validation8도 개발에 노출된 자료다. 주 평가100은 기존 질문·하위질문 family와 겹치지 않게 사전 선택했으며 학습·튜닝에 사용하지 않았다.

실행 흐름: 번호 선택 → 인자 생성 → 함수 호출

질문 + 관측 → reader prefill
hidden + KV cache
↓
action head → 합법 행동 중 argmax
0 keyword / 1 semantic / 2 read / 3 FINAL
↓
예: 번호 1 → semantic_search로 매핑
↓
고정 호출 구문을 batch 처리
같은 KV에서 LLM이 query 인자 생성
↓
인자 검증 → Python handler 실행
결과를 대화에 추가 → 다음 turn

번호도 도구 이름도 텍스트로 생성하지 않는다. head가 번호를 고르면 runtime이 도구 이름과 고정 구문을 공급한다. 이 구문은 한 번에 처리하고, 인자만 같은 KV cache에서 이어 생성한다. 줄어드는 것은 도구 선택·고정 구문의 순차 decoding이다. 인자와 최종 답변 생성은 남는다.

구분도구 선택·호출 구문LLM이 생성하는 부분
NativeLLM이 함께 생성<tool_call>{"name":"semantic_search","arguments":{"query":"Andrew Lang death year"}}</tool_call>
Decision headhead가 1 선택 → 코드가 semantic_search 구문 공급query": "Andrew Lang death year"}

Head는 {"까지 공급된 상태에서 이어 생성한다. 공백·줄바꿈을 생략한 설명용 예시이며 실제 raw는 아래에 있다.

KV 재사용은 같은 turn의 decision→인자/답변 사이에 적용된다. 다음 turn은 새 관측을 포함해 다시 prefill한다. FINAL은 답변 생성으로 분기한다.

학습·데이터 세부 설정

추가 read-slot head(2560→5)는 GENERATE 또는 관측 ID 후보 4개 중 하나를 고른다. action/read head는 독립 linear이며 공유 trainable trunk가 없다. 학습 파라미터는 총 23,049개다. action CE + read 상태의 slot CE, AdamW(lr 0.001, weight decay 0.01), 100 epochs, seed 20261016을 사용했다. 정규화 통계는 train에서만 계산했다.

학습 상태: keyword24 / semantic18 / read16 / FINAL24. read 라벨은 teacher 인자와 후보의 정확 일치로 만들었다. GENERATE5 / slot1 2 / slot2 6 / slot3 3 / slot4 0개로, 마지막 후보의 학습 양성이 없었다. 고정 validation 상태의 action macro-F1은 0.814였지만 자율 QA 성능과는 다른 지표다.

최종100은 answerable 2-hop dev 1,252개 중 기존 노출 제외 후 1,099개에서 hash 순서와 family 중복 배제로 선정했다. dev 전체의 무작위 표본이나 사전학습 비노출 표본은 아니다. Runtime에는 문단 ID·제목·본문만 제공하고 gold 답·support·질문 분해는 제외했다.

검색은 ID·제목·앞 300자 snippet을 반환한다. top_k는 기본 5(1–20), read는 1–8개 ID를 받는다. snippet만으로 답할 수도 있다. 도구 호출 합계는 226→239회로 늘었고, head는 100문항 모두 keyword 검색으로 시작했다. 빈 keyword 결과는 Native 23/84회, Head 29/101회였다. 따라서 이번 속도 차이를 호출 수 감소로 설명할 수 없다.

평균 시간은 26.8% 감소했고, 답변 점수는 비슷했다. F1 기준 5승·90동률·5패, EM 기준 Head만 정답 4문항·Native만 정답 3문항이었다. F1 차이 +0.46%p의 bootstrap 95% 구간은 −4.94~+5.96%p로, 품질 향상이나 비열등성을 입증하지는 못했다.

왜 빨라졌는가?

도구 호출 prefix는 호출당 13 tokens, 평균 2.39회 호출로 문항당 31.07 tokens였다. 이를 순차 생성 대신 batch로 처리했다. decoding 시간은 1.144→0.744초로 줄었고 prefix batch에 0.042초가 추가됐다. 전체 차이 0.358초와 정합적이다. 반면 입력 tokens는 3,914→4,106으로 늘었다. 전체 token이나 도구 수보다 순차 생성량 감소가 관측 시간 차이와 맞는다.

해석의 범위. 공유 GPU에서 질문·조건당 한 번 측정했으며 head와 함께 구문 처리·cache 연결·schema 제약도 바뀌었다. 26.8%를 head 단독의 통제된 속도 효과로 볼 수 없다. Native 형식 오류 4문항을 포함한 전체100이 주 분석이다. 오류 없는 96문항만 보는 사후 분석에서는 F1 차이 −0.57%p, EM 차이 0%p였다.

인자 선택까지 head에 맡기면?

read 인자 선택은 생성을 줄였지만 품질이 떨어져 채택하지 않았다. 같은 checkpoint의 validation8에서 F1이 21.88→9.38%로 하락했다. 기존20문항의 후속 ON/OFF 비교에서도 read15회 중 8회의 인자 생성을 생략했지만, 생성 tokens 60.55→57.00과 함께 F1 30.43→25.43%, EM 25→20%로 떨어졌다. 최종100에서는 검색·read 인자를 모두 LLM이 생성했다.

별도의 trajectory 단축 probe에서는 중간 단계 대체가 유효한 문항이 1개로 사전 기준 3개에 미달했다. 압축 정책·RL은 학습하지 않았다. 모든 실패 결과는 기존 보고서에 보존했다.

IMPLICATIONS

4. 시사점과 다음 검증

도구 선택의 텍스트 생성을 줄이는 구조는 동작했다. 그러나 인자·답변 생성 비용은 남고, 현재 모방 학습만으로 더 나은 정책이 만들어졌다고 보기는 어렵다. 후속 작업은 세 가지로 좁힌다.

  1. 최적화된 Native와 비교. 동일한 구문 처리·cache·schema 제약을 제공해도 head가 시간이나 품질에서 추가 이득을 주는지 확인한다.
  2. 행동 라벨을 최종 효용에 연결. train에서 현재 head가 방문한 상태의 대안 행동을 실행하고, 남은 episode의 정답·근거·비용으로 학습한다. 단순 teacher 모방, 성공-only 모방, 행동별 가치 학습을 같은 예산으로 비교한다.
  3. 필요할 때 구조를 확장. 먼저 빈 검색·남은 budget 같은 공개 상태 정보를 보강한다. read 후보 scoring이나 head-only RL은 이득의 여지가 확인된 뒤 검토한다. 다른 agent loop 전이는 별도 과제에서 평가한다.

위 항목은 제안이며 실행 결과가 아니다. 현재 정책으로 만든 행동 가치는 새 정책에서도 그대로 유지되지 않으므로, 개선 head는 episode 전체를 다시 평가해야 한다. 기존 평가100은 후속 학습에 사용하지 않는다.

관련 연구와 기여 범위

LAnR는 latent retrieval·경량 제어, GRASP는 검색·읽기 정책 학습, Stop-RAG는 추가 검색의 가치와 종료를 다룬다. FORGE의 frozen LLM routing, AggreVaTe/NRPI의 cost-to-go 학습도 관련된다.

작은 head나 생성 생략 자체보다, 최적화된 Native보다 좋은 품질–비용 곡선을 적은 학습·수집 비용으로 만드는지가 연구 기여의 기준이다. 현재 결과는 그 가능성을 살펴본 파일럿이다.
