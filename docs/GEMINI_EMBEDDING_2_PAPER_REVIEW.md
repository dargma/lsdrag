# Gemini Embedding 2 논문 리뷰

**Gemini Embedding 2는 텍스트·이미지·오디오·영상과 이들의 혼합 입력을 같은 벡터 공간에서 검색하도록 학습한 임베딩 모델이다.** 핵심은 Gemini의 멀티모달 표현을 양방향 인코딩과 대조학습으로 검색에 맞추고, 원본 모달리티를 텍스트로 변환하는 중간 단계를 줄이는 것이다.

**현재 저장소에서 측정한 EmbeddingGemma 2와는 다른 모델이다.** 아래 수치는 논문 저자의 결과이며, 이 저장소의 M3DocVQA 정답률 7%를 Gemini Embedding 2의 성능으로 해석하면 안 된다.

## 2. 문제 설정: 무엇이 새로운가?

기존 이미지–텍스트 임베더는 보통 각 모달리티를 별도로 인코딩해 같은 공간에 정렬한다. 이 방식은 교차 검색에는 유용하지만, 질문 텍스트와 이미지가 함께 주어졌을 때 둘 사이의 관계를 입력 내부에서 충분히 표현하기 어렵다는 것이 논문의 출발점이다.

Gemini Embedding 2는 이미지·오디오·영상 등을 Gemini가 처리하는 토큰 시퀀스로 변환해 **혼합 입력 내부의 상호작용까지 반영한 벡터 하나**를 만든다. 지원하는 검색 유형은 다음과 같다.

| 검색 유형 | 예 |
|---|---|
| 같은 모달리티 | 이미지로 비슷한 이미지 찾기 |
| 서로 다른 모달리티 | 텍스트 질문으로 이미지·영상 찾기, 음성 질문으로 텍스트 찾기 |
| 혼합 입력 | 사진 + 질문 텍스트로 관련 답변 문서 찾기 |

여기서 ‘native’는 원본 미디어를 모델의 모달리티 경로로 처리한다는 뜻이다. 전처리가 전혀 없다는 뜻도, 이미지의 모든 세부 정보가 손실 없이 보존된다는 뜻도 아니다. [원문 §1–3](https://arxiv.org/html/2605.27295v1#S3)

## 3. 모델 구조

### 3.1. 입력에서 검색 벡터까지

```text
텍스트 / 이미지 / 오디오 / 영상 / 이들의 혼합
                    ↓
          모달리티별 토큰 변환
                    ↓
 Gemini에서 초기화한 양방향 attention Transformer
                    ↓
       토큰별 문맥 표현 (L × d_model)
                    ↓
            Mean pooling
                    ↓
              선형 투영
                    ↓
           3,072차원 검색 벡터
```

| 단계 | 논문 설명 | 의미 |
|---|---|---|
| 초기화 | Gemini 파라미터에서 시작 | 기존 멀티모달·다국어 지식 활용 |
| 토큰화 | Gemini의 미디어 처리 경로 사용 | 원본 이미지·영상·오디오를 직접 입력 가능 |
| 표현 계산 | **양방향 attention** Transformer | 앞뒤 토큰 문맥을 함께 이용한 인코딩 |
| 요약 | 토큰 표현의 **평균 풀링** | 입력 전체를 벡터 하나로 압축 |
| 출력 | 무작위 초기화한 선형 projection을 학습 | 목표 출력 차원으로 변환 |

수식을 읽는 순서는 **토큰별 표현 → 평균 → 선형 투영**이다. 아래에서 굵은 글자는 벡터·행렬을 뜻한다.

$$
\mathbf{H}=\mathcal{M}(\mathbf{T})\in\mathbb{R}^{L\times d_{\mathcal{M}}}
$$

$$
\bar{\mathbf{h}}=\frac{1}{L}\sum_{\ell=1}^{L}\mathbf{h}_{\ell},
\qquad
\mathbf{E}=f(\bar{\mathbf{h}})\in\mathbb{R}^{d},
\qquad d=3072
$$

| 기호 | 뜻 | 모양·단위 |
|---|---|---|
| $\mathbf{T}$ | 미디어를 변환한 입력 토큰 시퀀스 | 유효 토큰 $L$개 |
| $\mathcal{M}$ | Gemini에서 초기화한 양방향 Transformer | 학습할 모델 |
| $\mathbf{h}_{\ell}$ | 입력 전체 문맥을 반영한 $\ell$번째 토큰의 표현 | $d_{\mathcal{M}}$차원 벡터 |
| $\mathbf{H}$ | 토큰별 표현을 쌓은 행렬 | $L\times d_{\mathcal{M}}$ |
| $\bar{\mathbf{h}}$ | 토큰 표현을 평균한 입력 전체 표현 | $d_{\mathcal{M}}$차원 |
| $f$ | 학습하는 선형 투영 | 출력 차원으로 변환 |
| $\mathbf{E}$ | 검색에 저장하거나 사용하는 최종 임베딩 | $d=3072$차원 |

**평균 풀링은 단어 자체를 평균하는 것이 아니다.** 문맥을 반영해 이미 계산한 토큰 벡터를 평균한다. 혼합 입력에서는 이미지·텍스트를 함께 처리한 표현이므로, ‘이 사진에서 왼쪽 물체’ 같은 입력 내부 관계도 표현에 반영될 수 있다. 패딩까지 무조건 더한다는 뜻은 아니며, 논문은 이를 길이 $L$의 시퀀스로 간단히 표기했다.

설명용으로 토큰 표현이 $(2,0)$, $(0,2)$라면 평균은 $(1,1)$이다. 실제 모델의 hidden 차원이 2라는 뜻은 아니다. 선형 투영은 이렇게 얻은 평균 벡터에 **학습된 행렬 변환**을 적용하는 단계이며, 3,072차원에 맞춰 단순히 0을 붙이는 처리가 아니다. [원문 §3.1](https://arxiv.org/html/2605.27295v1#S3.SS1)

정확한 Gemini 초기 체크포인트, 파라미터 수, 층수, hidden 차원 등은 이 논문의 구조 설명에 공개되어 있지 않다. **EmbeddingGemma 2의 24층·768차원 설정을 이 모델에 옮겨 적으면 안 된다.**

### 3.2. 왜 텍스트로 이미지를 검색할 수 있는가?

텍스트 질문과 이미지를 각각 **같은 Gemini Embedding 2**로 인코딩하고, 두 벡터의 코사인 유사도로 순위를 매긴다. 학습 과정에서 관련된 텍스트–이미지 등을 가깝게, 관련 없는 쌍을 멀게 만들어 교차 모달 정렬을 얻는다.

따라서 이미지 캡션에 정답 단어가 반드시 있어야 하는 것은 아니다. 반대로, 공통 공간이라고 해서 모든 미세한 위치·개수·시간 관계를 정확히 검색한다고 보장할 수도 없다. 최종 답변은 별도 Reader가 검색 근거를 해석해야 한다.

## 4. 학습 수식 자세히 읽기

이 절의 목표는 **관련된 질문·대상의 벡터는 가깝게, 비관련 대상의 벡터는 멀게 만드는 학습**을 이해하는 것이다. 원문 식 1–3을 계산 순서에 맞춰 나눴으며, 숫자 예시와 미분 설명은 이해를 돕기 위한 추가 설명이다.

### 4.1. 먼저 ‘입력’과 ‘벡터’를 구분한다 — 원문 식 1

$$
\mathbf{q}_i
=f\!\left(\operatorname{mean\_pool}\!\left(\mathcal{M}(t\oplus q_i)\right)\right)
$$

$$
\mathbf{p}_i^{\pm}
=f\!\left(\operatorname{mean\_pool}\!\left(\mathcal{M}(p_i^{\pm})\right)\right)
$$

| 기호 | 뜻 | 예 |
|---|---|---|
| $i$ | 배치 안에서 몇 번째 학습 예제인지 | 첫 번째 질문·정답 쌍 |
| $q_i$ / $\mathbf{q}_i$ | 원본 질문 / 질문을 인코딩한 벡터 | “풍차가 있는 만화 표지” / 그 질문 벡터 |
| $p_i^+$ / $\mathbf{p}_i^+$ | 관련 대상 / 그 대상 벡터 | 풍차가 있는 표지 이미지 |
| $p_i^-$ / $\mathbf{p}_i^-$ | 어려운 비관련 대상 / 그 벡터 | 분위기는 비슷하지만 풍차는 없는 표지 |
| $t$ | 텍스트 과제의 목적을 알리는 문자열 | 검색·질의응답 등 |
| $\oplus$ | 문자열·입력을 이어 붙이는 연산 | task 문자열 + 질문 |
| $\pm$ | $+$인 경우와 $-$인 경우를 한꺼번에 표기 | 더하기·빼기를 수행하라는 뜻이 아님 |

질문과 대상은 같은 모델을 사용하지만 입력 형식이 같아야 하는 것은 아니다. 질문이 텍스트이고 대상이 이미지여도 된다. 모델은 두 입력을 같은 출력 공간에 놓도록 학습한다. 텍스트 과제의 task 문자열은 학습 중 일부를 무작위로 제거하며, 이미지에 텍스트 task 문자열을 무조건 붙인다는 뜻은 아니다. [원문 §3.2, 식 1](https://arxiv.org/html/2605.27295v1#S3.SS2)

### 4.2. 두 벡터가 얼마나 비슷한가? — 코사인 유사도

$$
\operatorname{sim}(\mathbf{x},\mathbf{y})
=\frac{\mathbf{x}^{\top}\mathbf{y}}
{\lVert\mathbf{x}\rVert_2\,\lVert\mathbf{y}\rVert_2}
$$

분자는 같은 좌표끼리 곱해 더한 **내적**이고, 분모는 두 벡터의 길이를 곱한 값이다. 크기보다 방향이 비슷한지를 비교하며 값은 $-1$부터 $1$ 사이다. $1$은 같은 방향, $0$은 직교, $-1$은 반대 방향이다. **0.8이라는 값이 ‘80% 정답 확률’을 뜻하지는 않는다.**

설명용 2차원 예시에서 질문 벡터가 $(1,0)$이고 이미지 벡터가 $(0.8,0.6)$이면 둘 다 길이가 1이므로 유사도는 0.8이다. 이미지 벡터가 $(0,1)$이면 유사도는 0이다.

미리 길이가 1이 되도록 L2 정규화하면 다음처럼 내적만 계산해도 된다.

$$
\hat{\mathbf{x}}=\frac{\mathbf{x}}{\lVert\mathbf{x}\rVert_2},
\qquad
\operatorname{sim}(\mathbf{x},\mathbf{y})
=\hat{\mathbf{x}}^{\top}\hat{\mathbf{y}}
$$

**학습 때는 이 유사도로 손실을 계산하고, 검색 때는 이 유사도로 후보를 정렬한다.** 검색 중에 질문마다 모델을 다시 학습하는 것은 아니다.

### 4.3. 정답 대상에 얼마나 높은 점수를 줬는가? — 원문 식 2

먼저 유사도를 양수 점수로 바꾼다. 여기서 $\exp(a)=e^a$다.

$$
s_i^+=\operatorname{sim}(\mathbf{q}_i,\mathbf{p}_i^+),
\qquad
u_i^+=\exp(s_i^+/\tau)
$$

$\tau>0$는 **대조학습의 온도**다. 작으면 유사도 차이를 지수 함수가 더 크게 벌려 점수가 뾰족해진다. Reader VLM이 답변을 생성할 때 쓰는 temperature와는 별개다. 논문에서 공개하지 않은 실제 온도 값을 아래 예시 값으로 대신 주장하지 않는다.

다음은 정답·hard negative·배치 내 다른 대상 점수를 모두 더한 분모다. 긴 식을 읽기 쉽게 $Z_i$라는 이름을 붙였으며, 원문 식 2의 분모와 같다.

$$
\begin{aligned}
Z_i &= u_i^+
+ \exp\!\left(\frac{\operatorname{sim}(\mathbf{q}_i,\mathbf{p}_i^-)}{\tau}\right)\\
&\quad + \sum_{j=1}^{B}m_{ij}\,
\exp\!\left(\frac{\operatorname{sim}(\mathbf{q}_i,\mathbf{p}_j^+)}{\tau}\right)
\end{aligned}
$$

| 분모의 항 | 의미 | 왜 필요한가? |
|---|---|---|
| $u_i^+$ | 현재 질문의 정답 대상 점수 | 정답도 경쟁 후보에 포함 |
| hard negative 항 | 헷갈리도록 선정한 오답 대상 점수 | 쉬운 오답만 구분하는 모델이 되지 않게 함 |
| $j$에 대한 합 | 같은 배치에 있는 다른 예제의 정답 대상 점수 | 추가 대상을 효율적으로 negative로 활용 |
| $m_{ij}$ | 포함 여부를 정하는 0/1 마스크 | 사실상 정답인 대상을 잘못 negative로 쓰지 않게 함 |
| $B$ | 한 배치의 예제 수 | 마지막 합의 범위 |

hard negative가 없는 예제에서는 **해당 항 자체를 제외**한다. 누락된 벡터를 0벡터로 채운다는 뜻이 아니다.

정답 점수가 전체 후보 점수에서 차지하는 비중을 $P_i^+$로 쓰면 손실은 다음과 같다.

$$
P_i^+=\frac{u_i^+}{Z_i},
\qquad
\ell_i=-\log P_i^+,
\qquad
\mathcal{L}=\frac{1}{B}\sum_{i=1}^{B}\ell_i
$$

$P_i^+$는 **현재 후보 묶음 안에서의 정답 선택 비중**이다. 실제 서비스에서 답이 맞을 보정된 확률은 아니다. 정답 점수가 경쟁 후보보다 커지면 $P_i^+$가 1에 가까워지고, 자연로그를 쓴 손실은 0에 가까워진다. 오답 점수가 크면 손실이 커진다. 마지막에는 배치의 손실을 평균한다. [원문 식 2](https://arxiv.org/html/2605.27295v1#S3.SS2)

### 4.4. 숫자로 계산하면

**설명용 가상 예시**다. 한 텍스트 질문에 이미지 후보 3개가 있고, 학습 온도를 0.1로 둔다. 두 오답 모두 마스크에 의해 포함된다고 가정한다.

| 후보 | 역할 | 유사도 | 온도로 나눈 값 | 지수 점수 |
|---|---|---:|---:|---:|
| 풍차가 있는 표지 | 정답 | 0.8 | 8 | 약 2,980.96 |
| 비슷하지만 풍차 없는 표지 | hard negative | 0.7 | 7 | 약 1,096.63 |
| 다른 예제의 정답 이미지 | 배치 내 negative | 0.2 | 2 | 약 7.39 |

$$
P_i^+
=\frac{e^8}{e^8+e^7+e^2}
\approx 0.730,
\qquad
\ell_i\approx 0.315
$$

정답의 유사도가 가장 높아도 hard negative가 가까워 손실이 남는다. 학습으로 정답 유사도가 0.9, 두 오답이 0.4·0.2가 되면 다음처럼 바뀐다.

$$
P_i^+
=\frac{e^9}{e^9+e^4+e^2}
\approx 0.992,
\qquad
\ell_i\approx 0.0076
$$

이렇게 정답과 오답 사이의 **간격을 더 분명하게 만드는 것**이 대조학습의 목적이다. 예시의 표지는 개념 설명용이며, 실제 Aria 실험의 유사도나 이 논문의 학습 데이터를 재현한 수치가 아니다.

### 4.5. 왜 벡터가 가까워지고 멀어지는가?

위 손실을 유사도에 대해 미분하면 방향을 볼 수 있다. 아래는 식 2에서 따라오는 설명이며 논문이 별도 실험으로 보고한 결과는 아니다. $P_i^-$는 분모에 포함된 특정 오답 후보의 점수 비중이다.

$$
\frac{\partial\ell_i}{\partial s_i^+}
=\frac{P_i^+-1}{\tau},
\qquad
\frac{\partial\ell_i}{\partial s_i^-}
=\frac{P_i^-}{\tau}
$$

정답 쪽 미분은 0 이하이므로 경사하강법은 정답 유사도를 올리는 방향으로, 오답 쪽 미분은 0 이상이므로 오답 유사도를 내리는 방향으로 작용한다. 특히 **높은 점수를 받은 헷갈리는 오답**은 더 큰 학습 신호를 만든다. 실제 업데이트는 벡터 값만 직접 고치는 것이 아니라, 역전파로 벡터를 만드는 모델 파라미터를 바꾼다.

### 4.6. 정답을 오답 취급하지 않기 — 원문 식 3

$$
m_{ij}=\begin{cases}
0, & q_i=q_j\;\text{or}\;p_i^+=p_j^+,\\
1, & \text{otherwise}.
\end{cases}
$$

같은 질문이거나 같은 정답 대상을 공유하면 해당 배치 대상을 negative 합에서 제외한다. 특히 $i=j$인 자기 자신의 정답도 제외하므로 정답 항을 이중으로 세지 않는다.

예를 들어 텍스트 분류에서 두 질문의 정답 레이블이 모두 ‘스포츠’라면, 한 질문 입장에서 다른 예제의 ‘스포츠’를 오답으로 밀어내면 안 된다. 이 마스크가 그 충돌을 막는다. 다만 원문의 조건은 같은 질문·같은 정답 여부이며, 의미가 비슷한 모든 false negative를 자동으로 완벽히 발견한다는 뜻은 아니다. [원문 식 3](https://arxiv.org/html/2605.27295v1#S3.SS2)

### 4.7. 작은 벡터도 잘 작동하게 만들기 — MRL

기본 벡터의 앞 768개·1,536개 좌표에도 검색 정보를 담도록, 여러 길이에서 각각 대조학습 손실을 계산한다.

$$
\mathbf{E}^{(k)}=\mathbf{E}_{1:k},
\qquad
k\in\{768,1536,3072\}
$$

$$
\mathcal{L}_{\mathrm{MRL}}
=\sum_{k\in\{768,1536,3072\}}\lambda_k\,
\mathcal{L}_{\mathrm{NCE}}^{(k)}
$$

위 합은 원문의 ‘여러 겹치는 차원 구간에 손실 적용’을 풀어 쓴 **설명용 표현**이다. $\lambda_k$는 각 길이의 손실 가중치를 나타내며, 논문이 이 가중치의 정확한 값까지 공개했다는 뜻은 아니다.

앞 768차원은 앞 1,536차원 안에 있고, 둘 다 전체 3,072차원 안에 있다. 따로 학습한 모델 3개나 임의의 768개 좌표 선택이 아니다. 작은 차원만으로도 정답·오답을 구분해야 하므로, 중요한 검색 정보가 벡터 앞부분에도 담기도록 학습 압력을 준다.

차원을 줄이면 벡터 길이가 달라질 수 있으므로, 코사인 검색에는 정규화를 유지한다. 공식 Gemini Embedding 2 API는 요청한 축소 차원을 자동 정규화한다. 전체 벡터를 직접 잘랐다면 직접 다시 정규화한다. 질문과 검색 대상은 **같은 모델·같은 차원**을 사용해야 한다.

float32 벡터의 원시 저장량은 다음과 같다.

$$
3072\times4=12288\;\text{bytes},
\qquad
768\times4=3072\;\text{bytes}
$$

즉 768차원은 원시 벡터 저장량이 4분의 1이다. 인덱스·메타데이터·원본 파일 비용이나 실제 검색 속도까지 4배 개선된다는 뜻은 아니다. [원문 MRL 설명](https://arxiv.org/html/2605.27295v1#S3.SS2) · [API 정규화 동작](https://ai.google.dev/gemini-api/docs/embeddings#ensuring-quality-for-smaller-dimensions)

## 5. 학습 절차

| 단계 | 데이터·절차 | 목적 |
|---|---|---|
| Gemini 초기화 | 기존 멀티모달 모델에서 시작 | 기초 의미·시각·언어 능력 활용 |
| Pre-Fine-Tuning(PFT) | 이미지·텍스트·코드 과제, 많은 noisy query–target 쌍, 큰 배치 | 생성 모델을 인코딩에 적응 |
| Fine-Tuning(FT) | 텍스트·코드·문서·이미지·오디오·영상; 일부 과제는 hard negative 포함 | 다양한 모달리티와 검색 과제 정렬 |
| Model soup | 같은 실행·다른 실행의 체크포인트 가중치 평균 실험 | 특정 과제 개선과 일반화의 균형 |

각 학습 배치는 **하나의 과제**에서 표본을 뽑고, 여러 종류의 배치를 반복해 multi-task 학습한다. 한 배치 안에 모든 모달리티를 무조건 섞는다는 뜻은 아니다. task sampling 비율과 배치 크기에 따라 모달리티별 성능 균형이 민감하다고 보고한다.

Model soup는 여러 모델의 출력 벡터를 합치는 추론 앙상블이 아니라 **파라미터를 평균하는 것**이다. 최종 서비스 모델의 정확한 구성 비율까지 모두 공개된 것은 아니다. [원문 §3.3](https://arxiv.org/html/2605.27295v1#S3.SS3)

## 8. 평가 지표를 읽는 방법

| 지표 | 의미 | 현재 저장소와의 관계 |
|---|---|---|
| Recall@K | 정답 검색 대상이 상위 K 안에 있는 비율; 정확한 집계는 벤치마크 규칙 적용 | Reader에 실제 이미지가 전송됐는지까지 측정하지 않음 |
| NDCG@10 | 관련도가 높은 대상이 상위에 있는지를 평가하는 순위 지표 | 답변 EM과 다름 |
| MRR@10 | 상위 10개에서 첫 정답의 역순위 | 음성 전사 정확도가 아님 |
| MTEB 평균 | 여러 과제의 점수를 지정 방식으로 평균 | 하나의 RAG 정답률로 읽으면 안 됨 |

현재 보고서의 **이미지 전달 recall**은 풀이 전체에서 Reader가 실제 받은 정답 이미지의 비율이다. 논문의 검색 Recall@1·@5·@20과 분모·평가 단계가 다르다.

## 9. API 사용 정보 — 논문과 별도 확인

아래는 **2026-10-14 공식 API 문서** 기준이며 논문의 실험 설정과 구분한다.

| 항목 | 확인한 API 동작 |
|---|---|
| 모델 ID / 기본 차원 | `gemini-embedding-2` / 3,072 |
| 권장 출력 차원 | 768·1,536·3,072; 요청한 축소 차원도 API가 정규화 |
| 전체 입력 한도 | 8,192 tokens |
| 미디어 한도 | 이미지 최대 6개; PDF 1개·최대 6쪽; 오디오 180초; 영상 120초·최대 32프레임 |
| 텍스트 과제 | task_type 인자 대신 질문·문서 prefix 사용 |
| 혼합 입력 | 한 입력으로 묶은 여러 모달리티는 통합 벡터 하나 생성 |

텍스트 검색 예시는 질문에 `task: search result | query: ...`, 문서에 `title: ... | text: ...`를 붙인다. 이미지+텍스트 혼합 입력의 텍스트 부분에는 과제 prefix를 일률적으로 붙이지 않도록 안내한다. 기존 `gemini-embedding-001`과는 벡터 공간이 호환되지 않는다. API의 입력 묶음과 개별 embedding 단위를 확인해 여러 사진이 의도치 않게 벡터 하나로 합쳐지지 않게 해야 한다. [공식 API 문서](https://ai.google.dev/gemini-api/docs/embeddings)

API 가격·지연·실제 처리량은 이 리뷰에서 측정하지 않았다. 로컬 EmbeddingGemma 2와 비용·속도가 같다고 볼 근거도 없다.

## 10. 한계와 검토 의견

- **검색 성능과 답변 성능의 차이:** M3DocVQA에서 같은 Reader·도구로 직접 비교한 결과가 없다. 높은 ViDoRe나 MSCOCO 점수를 현재 A-RAG의 정답률 향상으로 변환할 수 없다.
- **재현 정보 부족:** 파라미터 규모, 정확한 Gemini 초기 모델, 전체 데이터 구성·비율, 학습량, soup 가중치 등이 충분히 공개되지 않아 논문만으로 같은 모델을 학습하기 어렵다.
- **수치 비교 범위:** 기준선 일부는 API 실행, 일부는 자가 보고다. 모든 과제의 최고가 아니고, 공통 과제 평균·과제 유형 평균·전체 과제 평균도 다르다.
- **본문·표의 차이:** Table 2의 이전 모델 평균과 본문 값, Table 1과 Table 6의 영상 기본값은 구분해 읽어야 한다.
- **원인 분리의 한계:** 합성 데이터·모달리티 혼합·도메인 FT·soup 효과를 제시하지만, 모든 구성 요소를 동일 예산으로 독립 통제한 것은 아니다. 음성 개선의 세부 원인도 표 하나로 확정할 수 없다.
- **혼합 입력 평가 범위:** EncyclopedicVQA 등은 유용하지만, 복잡한 멀티 이미지 비교·긴 시간 순서·표·세부 개수 문제 전체를 대변하지 않는다. 저자도 interleaved 입력의 새 평가 체계를 향후 과제로 제안한다.
- **서비스 측면:** 긴 문서를 단일 벡터로 압축할 때의 정보 손실, chunk 크기, 검색 후보 수, 지연·비용은 별도 시스템 평가가 필요하다.

위 한계는 원문을 검토한 의견이며, 저자가 모두 동일한 문구로 선언한 내용은 아니다. API 요청이나 새 벤치마크 실행을 이 문서 작성 과정에서 수행하지 않았다.

## 11. 현재 A-RAG에 주는 시사점과 다음 비교 제안

**텍스트 질문으로 실제 이미지 벡터를 검색하는 설계는 Gemini Embedding 2에서도 가능하다.** 기존 G1의 검색·청크 연결·이미지 전달 구조를 유지하면서 임베더와 인덱스를 새 모델로 교체하는 비교가 합리적이다. 다만 아래는 **아직 실행하지 않은 제안**이다.

| 유지할 것 | 바꿀 것 | 따로 측정할 것 |
|---|---|---|
| 질문 텍스트만 입력 | Gemini Embedding 2 query 벡터 | 모델 교체 효과 |
| 같은 문서·chunk·figure ID | 같은 모델로 텍스트·이미지 재인코딩 | 검색 근거 차이 |
| 기존 두 채널 검색·RRF 규칙 | 새 모델 전용 텍스트·이미지 인덱스 | 최종 답변 EM·F1·이미지 전달 recall |
| 같은 Gemma 4 E4B-it Reader·iteration·프롬프트 | API 어댑터·cache·실행 manifest | 임베딩 비용·지연·실패율 |

먼저 **텍스트 검색만 / 텍스트+이미지 검색**을 같은 Gemini Embedding 2 안에서 나눠 비교하고, 현재 EmbeddingGemma 2 결과와도 구분한다. 동일 768차원으로 비교하더라도 모델별 벡터 공간은 별개이므로 각자 인덱스를 사용한다. 오래된 인덱스에 새 질문 벡터만 넣으면 안 된다.

사진·페이지의 텍스트와 픽셀을 **한 입력으로 함께 인코딩**하는 방식은, 두 인덱스의 순위를 합치는 현재 G1과 다른 변경이다. 이를 검증하려면 별도 조건으로 분리해야 어떤 변화가 효과를 냈는지 알 수 있다. 완료 문항 재측정은 별도 승인 범위에서만 수행한다.
