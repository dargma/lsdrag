# Gemini Embedding 2 논문 리뷰

**Gemini Embedding 2는 텍스트·이미지·오디오·영상과 이들의 혼합 입력을 같은 벡터 공간에서 검색하도록 학습한 임베딩 모델이다.** 핵심은 Gemini의 멀티모달 표현을 양방향 인코딩과 대조학습으로 검색에 맞추고, 원본 모달리티를 텍스트로 변환하는 중간 단계를 줄이는 것이다.

**현재 저장소에서 측정한 EmbeddingGemma 2와는 다른 모델이다.** 아래 수치는 논문 저자의 결과이며, 이 저장소의 M3DocVQA 정답률 7%를 Gemini Embedding 2의 성능으로 해석하면 안 된다.

## 2. 문제 설정: 무엇이 새로운가?

기존 이미지–텍스트 임베더는 보통 각 모달리티를 별도로 인코딩해 같은 공간에 정렬한다. 이 방식은 교차 검색에는 유용하지만, 질문 텍스트와 이미지가 함께 주어졌을 때 둘 사이의 관계를 입력 내부에서 충분히 표현하기 어렵다는 것이 논문의 출발점이다.

Gemini Embedding 2는 이미지·오디오·영상 등을 Gemini가 처리하는 토큰 시퀀스로 변환해 **혼합 입력 내부의 상호작용까지 반영한 벡터 하나**를 만든다. 지원하는 검색 유형은 다음과 같다.

| 검색 유형 | 예 |
|---|---|
| 같은 모달리티 | 이미지로 비슷한 이미지 찾기 |
| 서로 다른 모달리티 | 텍스트 질문으로 이미지·영상 찾기, 음성 질문으로 텍스트 찾기 |
| 혼합 입력 | 사진 + 질문 텍스트로 관련 답변 문서 찾기 |

여기서 ‘native’는 원본 미디어를 모델의 모달리티 경로로 처리한다는 뜻이다. 전처리가 전혀 없다는 뜻도, 이미지의 모든 세부 정보가 손실 없이 보존된다는 뜻도 아니다. [원문 §1–3](https://arxiv.org/html/2605.27295v1#S3)

## 3. 모델 구조

### 3.1. 입력에서 검색 벡터까지

```text
텍스트 / 이미지 / 오디오 / 영상 / 이들의 혼합
                    ↓
          모달리티별 토큰 변환
                    ↓
 Gemini에서 초기화한 양방향 attention Transformer
                    ↓
       토큰별 문맥 표현 (L × d_model)
                    ↓
            Mean pooling
                    ↓
              선형 투영
                    ↓
           3,072차원 검색 벡터
```

| 단계 | 논문 설명 | 의미 |
|---|---|---|
| 초기화 | Gemini 파라미터에서 시작 | 기존 멀티모달·다국어 지식 활용 |
| 토큰화 | Gemini의 미디어 처리 경로 사용 | 원본 이미지·영상·오디오를 직접 입력 가능 |
| 표현 계산 | **양방향 attention** Transformer | 앞뒤 토큰 문맥을 함께 이용한 인코딩 |
| 요약 | 토큰 표현의 **평균 풀링** | 입력 전체를 벡터 하나로 압축 |
| 출력 | 무작위 초기화한 선형 projection을 학습 | 목표 출력 차원으로 변환 |

논문의 수식은 `E(x) = f(mean_pool(M(tokenize(x))))`다. 이미지 인코더 출력만 별도 평균하는 단순 late fusion과 달리, 혼합 시퀀스를 함께 처리한 문맥 표현에서 임베딩을 만든다. [원문 §3.1](https://arxiv.org/html/2605.27295v1#S3.SS1)

정확한 Gemini 초기 체크포인트, 파라미터 수, 층수, hidden 차원 등은 이 논문의 구조 설명에 공개되어 있지 않다. **EmbeddingGemma 2의 24층·768차원 설정을 이 모델에 옮겨 적으면 안 된다.**

### 3.2. 왜 텍스트로 이미지를 검색할 수 있는가?

텍스트 질문과 이미지를 각각 **같은 Gemini Embedding 2**로 인코딩하고, 두 벡터의 코사인 유사도로 순위를 매긴다. 학습 과정에서 관련된 텍스트–이미지 등을 가깝게, 관련 없는 쌍을 멀게 만들어 교차 모달 정렬을 얻는다.

따라서 이미지 캡션에 정답 단어가 반드시 있어야 하는 것은 아니다. 반대로, 공통 공간이라고 해서 모든 미세한 위치·개수·시간 관계를 정확히 검색한다고 보장할 수도 없다. 최종 답변은 별도 Reader가 검색 근거를 해석해야 한다.

## 4. 학습 목적: 대조학습과 MRL

### 4.1. NCE와 비관련 예제(negative)

학습 예제는 질문 `q`, 관련 대상 `p+`, 선택적인 어려운 비관련 대상 `p−`로 구성된다. 배치 안의 다른 예제의 정답 대상도 비관련 후보로 활용한다.

```text
loss = −log[
  exp(sim(q, p+) / τ)
  / (정답 점수 + hard-negative 점수 + 배치 내 negative 점수 합)
]
```

- `sim`은 코사인 유사도이며 `τ`는 온도다.
- hard negative가 없는 과제는 해당 항을 제외한다.
- 같은 질문이나 같은 정답 대상을 공유하는 배치 예제는 negative에서 제외한다. 같은 클래스 레이블을 잘못 밀어내는 문제를 줄이기 위한 장치다.
- 텍스트 과제에는 질문의 목적을 나타내는 task 문자열을 붙이고 학습 중 일부는 무작위로 제거한다. task 문자열이 없는 모달리티 입력에도 견고하게 만들기 위해서다.

[원문 §3.2, 식 1–3](https://arxiv.org/html/2605.27295v1#S3.SS2)

### 4.2. Matryoshka Representation Learning

기본 벡터는 **3,072차원**이고, 앞부분 **768·1,536차원**도 유용하도록 서로 겹치는 차원 구간에 대조학습 손실을 적용한다. 작은 벡터를 선택하면 저장·검색 비용을 줄일 수 있다.

float32 원시 벡터만 계산하면 한 항목당 3,072차원은 12,288바이트, 768차원은 3,072바이트로 **4분의 1**이다. 이는 차원 수로 계산한 저장량이며, 인덱스·메타데이터·원본 파일 비용이나 실제 검색 속도 측정값은 아니다. [원문 §3.2](https://arxiv.org/html/2605.27295v1#S3.SS2)

## 5. 학습 절차

| 단계 | 데이터·절차 | 목적 |
|---|---|---|
| Gemini 초기화 | 기존 멀티모달 모델에서 시작 | 기초 의미·시각·언어 능력 활용 |
| Pre-Fine-Tuning(PFT) | 이미지·텍스트·코드 과제, 많은 noisy query–target 쌍, 큰 배치 | 생성 모델을 인코딩에 적응 |
| Fine-Tuning(FT) | 텍스트·코드·문서·이미지·오디오·영상; 일부 과제는 hard negative 포함 | 다양한 모달리티와 검색 과제 정렬 |
| Model soup | 같은 실행·다른 실행의 체크포인트 가중치 평균 실험 | 특정 과제 개선과 일반화의 균형 |

각 학습 배치는 **하나의 과제**에서 표본을 뽑고, 여러 종류의 배치를 반복해 multi-task 학습한다. 한 배치 안에 모든 모달리티를 무조건 섞는다는 뜻은 아니다. task sampling 비율과 배치 크기에 따라 모달리티별 성능 균형이 민감하다고 보고한다.

Model soup는 여러 모델의 출력 벡터를 합치는 추론 앙상블이 아니라 **파라미터를 평균하는 것**이다. 최종 서비스 모델의 정확한 구성 비율까지 모두 공개된 것은 아니다. [원문 §3.3](https://arxiv.org/html/2605.27295v1#S3.SS3)

## 6. 주요 검색 결과

### 6.1. 이미지·영상·문서 검색

단위는 표에 적힌 지표의 점수이며, EM 같은 답변 정확도가 아니다. 비교 기준은 논문 Table 1에 함께 있는 모델 중 해당 행의 가장 높은 값이다.

| 검색 방향·벤치마크 | 지표 | Gemini Embedding 2 | 표 내 최강 비교 모델 | 차이 |
|---|---|---:|---|---:|
| 이미지→이미지 · GUIEC | Recall@1 | **79.4** | 기존 Google 모델 69.5 | +9.9 |
| 텍스트→이미지 · MSCOCO | Recall@1 | **62.9** | Voyage-3.5-multimodal 58.1 | +4.8 |
| 텍스트→이미지 · Flickr30k | Recall@1 | 89.1 | Voyage-3.5-multimodal **89.9** | −0.8 |
| 텍스트→이미지 · DOCCI | Recall@1 | **93.4** | Amazon Nova MME 84.0 | +9.4 |
| 이미지→텍스트 · MSCOCO | Recall@1 | **78.8** | Voyage-3.5-multimodal 74.5 | +4.3 |
| 텍스트→영상 · Vatex | NDCG@10 | **68.8** | Amazon Nova MME 60.3 | +8.5 |
| 텍스트→영상 · MSR-VTT | NDCG@10 | **68.0** | Amazon Nova MME 67.0 | +1.0 |
| 이미지+텍스트→텍스트 · EncyclopedicVQA | Recall@20 | **71.5** | Voyage-3.5-multimodal 58.6 | +12.9 |
| 문서 검색 · ViDoRe V2 | NDCG@10 | 64.9 | Voyage-3.5-multimodal **65.5** | −0.6 |

**모든 벤치마크에서 최고는 아니다.** 특히 문서 검색 ViDoRe V2와 텍스트→이미지 Flickr30k에서는 Voyage 쪽이 높다. 논문의 전반적 검색 평균은 77.2 대 Voyage 70.0, Amazon Nova 68.2이나, 별표 평균은 **모든 모델에 결과가 있는 공통 과제 교집합** 기준이므로 표의 모든 행을 단순 평균하면 안 된다. [원문 Table 1, §4.1](https://arxiv.org/html/2605.27295v1#S4.SS1)

이미지와 텍스트의 교차 검색은 각각 따로 인코딩해 전체 테스트 후보에서 코사인 유사도로 검색했다. 혼합 입력 평가는 이미지+질문을 함께 인코딩했다. 영상 검색은 **1 FPS, 최대 32프레임** 설정을 사용했다.

### 6.2. 텍스트·코드

| 평가 | Gemini Embedding 2 | 비교·주의 |
|---|---:|---|
| MTEB multilingual Mean(Task) | **69.9** | Table 2의 이전 Gemini Embedding은 68.4 |
| MTEB multilingual Mean(Type) | **61.2** | Mean(Task)와 다른 평균 방식 |
| MTEB Code v1 평균 | **84.0** | 코드 생성 정확도가 아닌 코드 검색 점수 |

본문은 이전 multilingual 평균을 68.32라고도 적지만 Table 2는 68.4로 표기한다. 리뷰는 표 값을 인용하며, 이를 임의로 일치시켜 정밀한 차이로 주장하지 않는다. Instruction Retrieval은 2.9로 이전 Gemini Embedding 5.2보다 낮아, 전체 평균 개선이 모든 능력의 개선을 뜻하지도 않는다. [원문 Table 2, §4.2](https://arxiv.org/html/2605.27295v1#S4.SS2)

### 6.3. 음성: ASR 뒤 텍스트 임베딩과 직접 음성 임베딩

같은 Gemini Embedding 2를 사용하되 입력 경로를 비교했다. 지표는 MSEB passage retrieval의 MRR@10이다.

| 입력 경로 | 전체 평균 | 동일 언어 | 교차 언어 |
|---|---:|---:|---:|
| 음성→ASR 텍스트→임베딩 | 70.40 | 73.58 | 67.55 |
| 원본 음성→임베딩 | **73.99** | **75.58** | **72.56** |
| 차이 | **+3.59** | **+2.00** | **+5.01** |

중간 전사가 잘못 확정한 단어에 검색이 끌려가는 문제를 줄일 수 있다는 해석이다. 다만 이 표만으로 운율·강세 보존이 향상의 정확한 원인이라고 분리 입증한 것은 아니다. 모든 ASR 시스템보다 항상 낫다는 뜻으로도 확대하지 않는다. [원문 Table 3, §4.3](https://arxiv.org/html/2605.27295v1#S4.SS3)

## 7. Ablation과 일반화

### 7.1. 전문 분야 이미지→텍스트 검색

| 분야·벤치마크 | Recall@5 |
|---|---:|
| 현미경·생물 · MicroVQA | **79.3** |
| 미술 · ArtCap | **67.7** |
| 천문 · AstroLLaVA | **64.4** |
| 요리 · Recipe1M 재료 / 조리법 | **90.2 / 92.1** |

비교한 CLIP·ALIGN·SigLIP 2·TIPS·일부 Voyage 결과보다 높은 값을 보고한다. 이는 해당 후보군에서의 검색 일반화 결과이며, 의료·과학 질문의 최종 답변 정확도나 전문가 수준 판단을 입증한 결과는 아니다. [원문 Table 4, §5.1](https://arxiv.org/html/2605.27295v1#S5.SS1)

### 7.2. 합성 데이터

세 가지 선택된 코드 검색 과제 평균은 다음과 같다. 이 ablation은 model soup를 제외했다.

| 설정 | 세 과제 평균 |
|---|---:|
| 이전 Gemini Embedding | 70.5 |
| Gemini Embedding 2, 합성 데이터 제외 | 73.0 |
| Gemini Embedding 2, 합성 데이터 포함 | **86.3** |

따라서 합성 데이터 유무의 차이는 **+13.3점**이고, 이전 모델 대비 차이는 **+15.8점**이다. 논문의 +15.8을 ‘합성 데이터만의 효과’라고 쓰면 비교 기준이 잘못된다. 이 세 과제 평균 86.3은 전체 MTEB Code 평균 84.0과도 구분한다. [원문 Table 5, §5.2](https://arxiv.org/html/2605.27295v1#S5.SS2)

### 7.3. PFT·FT와 영상 도메인 적응

FT는 영상 데이터가 추가되어 PFT보다 영상 과제에서 큰 개선을 보인다. 추가 도메인 학습과 model soup의 결과는 다음과 같다.

| Table 6 설정 | MSR-VTT | YouCook2 | Vatex |
|---|---:|---:|---:|
| 기본 | 68.2 | 55.9 | 69.2 |
| MSR-VTT+Vatex 데이터 추가 FT | 76.1 | 55.3 | 79.5 |
| 기본:추가 FT = 1:1 soup | 73.7 | **56.8** | 76.8 |

특정 도메인 점수를 높이면 다른 도메인이 낮아질 수 있고, 가중치 평균이 균형을 되찾는 예다. **Table 6 기본값은 Table 1의 MSR-VTT 68.0·YouCook2 52.5·Vatex 68.8과 다르다.** 원문이 이 차이를 충분히 설명하지 않으므로 서로 같은 체크포인트 결과로 합치지 않는다. [원문 Figure 3, Table 6, §5.3–5.4](https://arxiv.org/html/2605.27295v1#S5.SS4)

## 8. 평가 지표를 읽는 방법

| 지표 | 의미 | 현재 저장소와의 관계 |
|---|---|---|
| Recall@K | 정답 검색 대상이 상위 K 안에 있는 비율; 정확한 집계는 벤치마크 규칙 적용 | Reader에 실제 이미지가 전송됐는지까지 측정하지 않음 |
| NDCG@10 | 관련도가 높은 대상이 상위에 있는지를 평가하는 순위 지표 | 답변 EM과 다름 |
| MRR@10 | 상위 10개에서 첫 정답의 역순위 | 음성 전사 정확도가 아님 |
| MTEB 평균 | 여러 과제의 점수를 지정 방식으로 평균 | 하나의 RAG 정답률로 읽으면 안 됨 |

현재 보고서의 **이미지 전달 recall**은 풀이 전체에서 Reader가 실제 받은 정답 이미지의 비율이다. 논문의 검색 Recall@1·@5·@20과 분모·평가 단계가 다르다.

## 9. API 사용 정보 — 논문과 별도 확인

아래는 **2026-10-14 공식 API 문서** 기준이며 논문의 실험 설정과 구분한다.

| 항목 | 확인한 API 동작 |
|---|---|
| 모델 ID / 기본 차원 | `gemini-embedding-2` / 3,072 |
| 권장 출력 차원 | 768·1,536·3,072; 요청한 축소 차원도 API가 정규화 |
| 전체 입력 한도 | 8,192 tokens |
| 미디어 한도 | 이미지 최대 6개; PDF 1개·최대 6쪽; 오디오 180초; 영상 120초·최대 32프레임 |
| 텍스트 과제 | task_type 인자 대신 질문·문서 prefix 사용 |
| 혼합 입력 | 한 입력으로 묶은 여러 모달리티는 통합 벡터 하나 생성 |

텍스트 검색 예시는 질문에 `task: search result | query: ...`, 문서에 `title: ... | text: ...`를 붙인다. 이미지+텍스트 혼합 입력의 텍스트 부분에는 과제 prefix를 일률적으로 붙이지 않도록 안내한다. 기존 `gemini-embedding-001`과는 벡터 공간이 호환되지 않는다. API의 입력 묶음과 개별 embedding 단위를 확인해 여러 사진이 의도치 않게 벡터 하나로 합쳐지지 않게 해야 한다. [공식 API 문서](https://ai.google.dev/gemini-api/docs/embeddings)

API 가격·지연·실제 처리량은 이 리뷰에서 측정하지 않았다. 로컬 EmbeddingGemma 2와 비용·속도가 같다고 볼 근거도 없다.

## 10. 한계와 검토 의견

- **검색 성능과 답변 성능의 차이:** M3DocVQA에서 같은 Reader·도구로 직접 비교한 결과가 없다. 높은 ViDoRe나 MSCOCO 점수를 현재 A-RAG의 정답률 향상으로 변환할 수 없다.
- **재현 정보 부족:** 파라미터 규모, 정확한 Gemini 초기 모델, 전체 데이터 구성·비율, 학습량, soup 가중치 등이 충분히 공개되지 않아 논문만으로 같은 모델을 학습하기 어렵다.
- **수치 비교 범위:** 기준선 일부는 API 실행, 일부는 자가 보고다. 모든 과제의 최고가 아니고, 공통 과제 평균·과제 유형 평균·전체 과제 평균도 다르다.
- **본문·표의 차이:** Table 2의 이전 모델 평균과 본문 값, Table 1과 Table 6의 영상 기본값은 구분해 읽어야 한다.
- **원인 분리의 한계:** 합성 데이터·모달리티 혼합·도메인 FT·soup 효과를 제시하지만, 모든 구성 요소를 동일 예산으로 독립 통제한 것은 아니다. 음성 개선의 세부 원인도 표 하나로 확정할 수 없다.
- **혼합 입력 평가 범위:** EncyclopedicVQA 등은 유용하지만, 복잡한 멀티 이미지 비교·긴 시간 순서·표·세부 개수 문제 전체를 대변하지 않는다. 저자도 interleaved 입력의 새 평가 체계를 향후 과제로 제안한다.
- **서비스 측면:** 긴 문서를 단일 벡터로 압축할 때의 정보 손실, chunk 크기, 검색 후보 수, 지연·비용은 별도 시스템 평가가 필요하다.

위 한계는 원문을 검토한 의견이며, 저자가 모두 동일한 문구로 선언한 내용은 아니다. API 요청이나 새 벤치마크 실행을 이 문서 작성 과정에서 수행하지 않았다.

## 11. 현재 A-RAG에 주는 시사점과 다음 비교 제안

**텍스트 질문으로 실제 이미지 벡터를 검색하는 설계는 Gemini Embedding 2에서도 가능하다.** 기존 G1의 검색·청크 연결·이미지 전달 구조를 유지하면서 임베더와 인덱스를 새 모델로 교체하는 비교가 합리적이다. 다만 아래는 **아직 실행하지 않은 제안**이다.

| 유지할 것 | 바꿀 것 | 따로 측정할 것 |
|---|---|---|
| 질문 텍스트만 입력 | Gemini Embedding 2 query 벡터 | 모델 교체 효과 |
| 같은 문서·chunk·figure ID | 같은 모델로 텍스트·이미지 재인코딩 | 검색 근거 차이 |
| 기존 두 채널 검색·RRF 규칙 | 새 모델 전용 텍스트·이미지 인덱스 | 최종 답변 EM·F1·이미지 전달 recall |
| 같은 Gemma 4 E4B-it Reader·iteration·프롬프트 | API 어댑터·cache·실행 manifest | 임베딩 비용·지연·실패율 |

먼저 **텍스트 검색만 / 텍스트+이미지 검색**을 같은 Gemini Embedding 2 안에서 나눠 비교하고, 현재 EmbeddingGemma 2 결과와도 구분한다. 동일 768차원으로 비교하더라도 모델별 벡터 공간은 별개이므로 각자 인덱스를 사용한다. 오래된 인덱스에 새 질문 벡터만 넣으면 안 된다.

사진·페이지의 텍스트와 픽셀을 **한 입력으로 함께 인코딩**하는 방식은, 두 인덱스의 순위를 합치는 현재 G1과 다른 변경이다. 이를 검증하려면 별도 조건으로 분리해야 어떤 변화가 효과를 냈는지 알 수 있다. 완료 문항 재측정은 별도 승인 범위에서만 수행한다.
