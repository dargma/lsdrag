# GRPO 길이 보상: native ARAG vs head ARAG, LLM full fine-tuning (2026-11-03, 검토 반영본)

근거 자료
- 진단: `analysis/length_penalty_diagnosis.json`
- head 실행 경로 검증: `analysis/head_prefill_check.json`
- 검토: 범위 검토와 공평성 검토 에이전트 2개

## 1. 기존 GRPO에서 길이 penalty가 무효였던 원인

| 원인 | 근거 |
|---|---|
| 그룹 표준화 때문에 λ 크기가 무의미 | F1이 같은 그룹이 83%. λ를 .03에서 .3으로 올려도 어드밴티지 부호가 바뀌는 궤적은 3.6%, λ=3에서도 10% |
| 길이와 정확도가 같은 방향 | F1이 갈린 그룹에서 corr(호출 수, F1) = +0.34 |
| 줄일 수 있는 범위가 좁음 | 호출 2~3회가 91%. LLM이 고정이라 인자·답 길이는 불변 |
| 형식 토큰과 고정 prefix가 비용을 희석 | 생성 97토큰 중 답 본문은 4토큰, chunk ID와 JSON 문법이 55토큰. 입력의 57%는 매 단계 다시 세는 prompt |
| 다양성 부족 | head 최대 확률 0.92. 그룹의 39%는 4궤적 행동 순서가 같음 |
| format reward | 코드에 없음. 문법 강제로 형식 오류가 0이라 넣어도 신호 0. 대신 prompt의 "근거 부족 시 빈 답" 규칙 때문에 답의 25~34%가 빈 문자열 |

## 2. head 실행 경로 검증 (GPU, 8문항 28단계 + 저장된 1,037결정)

- **head 행동 실행**: head 행동과 실행된 도구가 100% 일치함. 예외는 인자가 토큰 한도에 걸린 오류 에피소드 1건뿐임.
- **강제 prefix**: 매 결정마다 `<tool_call>\n{"name": "X", "arguments": {"`를 KV cache에 prefill함. LLM은 인자만 생성하고, 생성 토큰에 도구 이름이 들어간 경우는 0건임.
- **단계 사이 prefill**: 매 단계 전체를 다시 prefill함. 결정적이고, 저장된 head 확률을 정확히 재현함(차이 0).
- **KV cache 이어붙이기로 바꿀 경우**
  - 생성 마지막 토큰 `}\n` 하나만 template의 재렌더링과 달라짐.
  - bf16 수치 차이로 head 확률이 평균 0.026, 최대 0.16 바뀜. 결정이 바뀐 비율은 7%(2/29)임.
  - **결론**: 학습된 head와 맞추려면 두 arm 모두 전체 re-prefill을 유지함.
- **arm 간 불일치**: head 모드의 FINAL은 `{"answer":`를 LLM이 생성하지만, native는 같은 토큰을 강제 prefix로 처리함. → head 모드도 `{"answer":`를 prefill함.

## 3. 실험

**질문**: 정확도 보상과 길이 보상으로 GRPO 학습(LLM full FT)을 하면, native와 head ARAG 각각에서 호출이 줄면서 정확도가 오르거나 유지되는가.

**run**

| run | 구성 | 비교 기준 |
|---|---|---|
| A1 | native ARAG. LLM이 결정과 payload를 생성. LLM full FT | 같은 arm의 iteration 0(base LLM) |
| B1 | head ARAG. KL0 GRPO head를 불러와 함께 학습. LLM full FT | 같은 arm의 iteration 0(base LLM + KL0 head) |

검토 결과 삭제한 항목
- λ=0 대조, head 고정 조건, T sweep, 답 토큰 penalty, train 문항 확장
- 이유: 질문에 직접 답하지 않는 ablation이거나, 동결 split과의 비교 가능성을 해침
- 예외: A1/B1이 양성으로 나오면 그때 λ=0 대조를 추가함

**보상과 어드밴티지**

$$R_i = \mathrm{F1}_i\big(1+\lambda(1-n_i/8)\big),\qquad A_i = R_i-\overline{R}_{\text{group}}\ (\text{std 나눗셈 없음})$$

- 정답일 때만 짧을수록 이득임. 빈 답이나 오답은 길이와 무관하게 0이라 "빨리 포기" 해킹이 생기지 않음.
- λ는 smoke 결과의 어드밴티지 분포로 0.3과 1 중 하나를 사전 확정함. λ=0.3이면 호출 1회 절감의 보너스가 0.04·F1로, 그룹 F1 std(0.06~0.13)보다 작음.

**공평성 규칙** (두 arm 동일)

| 항목 | 규칙 |
|---|---|
| 결정 샘플링 | native: 합법 도구 이름 분기 토큰에서 softmax(logits/T)로 샘플링. 분기 logprob의 합을 결정 logprob으로 기록. head: head 분포에서 샘플링. T=1.0 |
| payload | free 토큰을 T=1.0으로 샘플링하고 logprob을 기록. 문법이 강제한 토큰은 loss에서 제외. FINAL은 두 arm 모두 `{"answer":`를 강제 prefix로 둠 |
| loss | 결정 항과 payload 항 모두 PPO clip 0.2, 같은 A_i. 결정 하나는 항 1개 |
| 정규화 | 고정 상수 N(배치 궤적 수) |
| epoch | 결정과 payload 모두 반복당 1 pass |
| 엔트로피 bonus | 없음(두 arm 모두) |
| KL | 각 arm의 iteration 0 정책 대비 β 동일. native는 LLM 토큰 KL. head arm은 LLM 토큰 KL + head 행동 KL |
| lr | LLM 1e-6. head lr은 smoke에서 결정 변화율(반복당 결정 KL)이 native와 같은 수준이 되도록 정함 |
| prefill | 두 arm 모두 매 단계 전체 re-prefill |
| 토큰 보고 | 결정 토큰, 강제 토큰, free 생성 토큰, 입력 토큰을 따로 셈 |
| 예산 | 192문항 × 8궤적 × 4회, seed 동일, 8회 호출 후 FINAL 강제 |

**평가**
- dev64 greedy, iteration 0·2·4에서 평가함.
- **판정은 iteration 4로 고정함.** 최고 iteration을 고르는 선택 편향을 피하기 위함.

**판정 기준** (사전 등록, iteration 0 대비 paired bootstrap 95% CI)
- 짧아짐: 평균 호출 수 감소의 CI가 0을 포함하지 않음. 바닥 효과(2hop은 최소 2회, 현재 평균 2.4회) 때문에 "3회 이상 궤적 비율"을 함께 보고함.
- 정확도 유지: ΔF1 CI 하한 > −3%p
- 정확도 향상: ΔF1 CI 하한 > 0
- 보조 지표: EM, free 생성 토큰, 빈 답 비율, 결정 엔트로피, replay gap(rollout logprob과 재계산 logprob의 차이)

## 5. 사용자 판정 기준 (2026-11-03 확정)

- **best**: ARAG iteration(도구 호출)이 줄면서 정확도가 유지되거나 조금 오름
- **정확도**: 학습 전과 최소 동등 이상
- **inference time**: 20~50% 감소가 최적
- **경보 1**: iteration 수가 거의 그대로이고 길이도 변화가 없으면 학습이 안 되는 문제로 봄
- **경보 2**: 너무 급격히 짧아지면서 정확도가 떨어지면 붕괴로 봄

**inference time 분해** (dev64, 192 에피소드)
- 회귀식 `sec = 0.026·gen + 0.218·inp_k − 0.137·calls + 0.118`, R² 0.977
- 생성 토큰이 시간의 76%, 입력이 30%를 설명함. 생성 토큰 1개에 26ms
- 생성 97토큰의 구성: 검색 인자 42, chunk ID 문자열 44(read_chunk 21, support_ids 22), 문법 12, 답 4
- 3회 이상 호출 궤적을 모두 2회로 줄여도 시간 감소는 native 18%, head 4%임
- → 호출 수만 보상하면 20~50% 목표에 닿지 못함. 보상의 길이 항은 지연 시간 proxy로 둬야 함

**보상 수정안**
- `R = F1·(1 + λ·max(0, 1 − L/L_ref))`
- `L = 0.026·생성 토큰 + 0.218·입력 k토큰`(초 단위 proxy), `L_ref` = 학습 전 dev64 평균
- support_ids 비우기 방지: 답이 비어 있지 않으면 support_ids가 1개 이상이도록 문법으로 강제함

**모니터링** (매 iteration, train rollout과 dev64)
- 호출 수 분포, 3회 이상 비율, 생성 토큰 구성, L
- iteration 2에서 호출 수와 L의 변화가 5% 미만이면 경보 1
- 호출 수나 L이 50% 넘게 줄면서 F1이 내려가면 경보 2

## 6. 목표 수정 (2026-11-03, 사용자)

- **목표**: tool을 정확하게, 필요한 만큼만 사용하게 함. 길이 자체가 아니라 ARAG iteration(도구 호출 수)을 줄임
- **감소 목표**: 10~30%
- **보상**: `R = F1 · γ^(도구 호출 수)`, γ = 0.8
  - 정답일 때만 호출 1회마다 credit의 20%를 잃음
  - 정답은 항상 오답(0)보다 높음. 너무 적게 써서 틀리면 손해이고, 불필요하게 더 쓰면 감점임
  - 지연 시간 proxy는 보상에서 빼고 보고 지표로만 둠
- **smoke rollout 근거**
  - 호출 수가 다른 정답 궤적이 섞인 그룹은 native 25%, head 19%임
  - μ=0.2 수준에서 정답 궤적 사이 corr(A, 호출 수)는 −0.42 / −0.20임
  - 전체 corr(A, 호출 수)는 여전히 +0.1임. T가 높은 rollout에서 일찍 FINAL해 틀린 궤적 때문으로, "부족하게 쓰지 말라"는 신호임
- **경보 1**: iteration 2에서 dev64 호출 수 감소가 5% 미만이면 γ를 0.7로 낮추는 것을 검토함
- **경보 2**: 호출 수가 50% 넘게 줄면서 F1이 떨어지면 붕괴로 봄
- **실행**: 2026-11-03 11:54Z에 A1(native, T_dec 4.0)을 시작함. 이어서 B1(head, lr-head 5e-5)을 실행함
  - 공통 설정: β 0.02, lr 1e-6, 192×8×4, dev64 평가는 iteration 0·2·4
  - 이전의 latency 보상 A1 실행은 시작 직후 중단함(`results/_aborted_fullft_native_A1_latency`)

## 7. arm C 추가 (2026-11-03, 사용자)

- **근본 질문**: 추가한 select head가 도구 선택뿐 아니라 도구 호출을 효율적으로 하는 정책이 될 수 있는가
- **C1 구성**: reader LLM은 고정하고 select head만 학습함(`--freeze-llm`). B1과 같은 조건이고 LLM 업데이트만 없음
  - rollout 샘플링은 결정 head, payload T=1
  - head lr 5e-5, 보상 F1·0.8^calls, 192×8×4
  - B1과 C1을 비교하면 LLM 학습의 기여가 분리됨
- **동시 실행**: C1은 GPU 약 8~16GB만 써서 A1과 동시에 돌림(11:57Z 시작)
  - 동시 실행이라 dev64의 wall-clock 초는 비교할 수 없음
  - 시간은 호출 수, 토큰, 지연 proxy로 판정함. 필요하면 마지막에 GPU를 단독으로 쓰면서 다시 측정함
- **위험**: head lr 5e-5, 1 pass로는 head 변화가 작을 수 있음. head_changed_vs_loaded가 아주 작으면 경보 1로 봄. 원인이 능력 부족이 아니라 최적화 강도일 수 있다는 점을 명시함

## 8. 데이터셋 교체: mixed-hop (2026-11-03, 사용자 선택)

**2hop 진단**
- dev64에서 정답 근거 2문단을 모두 관측한 에피소드는 23%뿐이고, 62%는 1개만 관측함
- 근거를 다 본 뒤의 추가 호출은 전체 호출의 약 6%임
- 즉 불필요한 호출은 거의 없고 오히려 부족함. "필요한 만큼"이 모든 문항에서 약 2회로 같음
- 그래서 2hop A1·C1은 중단함(`results/_aborted_2hop_*`)

**새 split** `configs/split_mixhop.json` (`scripts/make_mixhop_split.py`, seed 20261103)
- 2hop 부분은 기존 split과 같음. 3hop·4hop은 MuSiQue answerable train에서 하위 유형별 층화 추출함
- train 576 (2hop / 3hop / 4hop 각 192), validation 192 (각 64), test 320 (160 / 80 / 80, 보류)
- 코퍼스는 train·dev 전체 문단이라 3·4hop 근거가 이미 포함됨. 다시 만들지 않음

**실행**
- 반복마다 train pool에서 hop별 64개씩 192문항을 새로 뽑음(`--resample`) × 8궤적 × 4회
- dev192 평가는 iteration 0·2·4에서 함
- A1 → B1은 순차, C1은 동시에 실행함. 12:02Z에 시작함
- head는 기존 KL0 head(2hop으로 학습)를 그대로 불러옴

**추가 지표**
- hop별 F1·호출 수
- 낭비 호출: 근거를 모두 본 뒤의 추가 호출
- 부족 종료: 근거를 모두 보기 전에 FINAL
- 이상적인 정책은 2hop에서 줄이고 3·4hop에서는 필요한 만큼 늘림

**①의 근거**
- **필요성**: 현재 보상에서는 결정의 51%가 학습 신호 0을 받음(그룹 전체가 0점이라서). 단계 보상에서는 11%로 줄어듦
- **정합성**: 같은 문항 그룹 안에서 근거 확보율과 F1의 상관이 +0.44
- **방향**: 현재 보상과 같은 방향을 2~4배 강하게 줌
  - semantic_search +, keyword_search −
  - 근거를 다 모으기 전의 FINAL −, 다 모은 뒤의 FINAL +
- **효과 예상**
  - 같은 그룹에서 낭비 호출이 없는 궤적은 낭비가 있는 궤적보다 호출이 1.0~1.3회 적고, F1은 +0.03~+0.09 높음
  - 낭비 호출(새 근거가 없는 호출)은 전체 호출의 47.5%
- **정의 수정**: 처음에는 read_chunk를 모두 낭비로 셌음. 이를 고쳐 정답 문단을 처음 전문으로 읽으면 0.5 credit을 줌

**C3 구성**
- C1과 같고 보상만 단계별 보상으로 바꿈
  - 호출마다 0.5·(새 근거 / 근거 수) − 0.05, 마지막에 F1
  - 어드밴티지는 return-to-go에서 같은 단계 위치의 그룹 평균을 뺌
- gold는 train에서만 쓰고 평가에는 쓰지 않음
- GPU 여유가 없어서(87/95GB) C2가 끝나면 smoke를 거쳐 자동 시작함

**C3 폐기** (2026-11-03, 사용자 지시): 시작 전에 대기 launcher를 중지함. 단계별 보상 구현(`--reward process`)과 오프라인 검증 결과는 코드와 `analysis/process_reward_validation.json`에 남김.

## 14. C2 최종 (head lr 2e-4, iteration 4)
