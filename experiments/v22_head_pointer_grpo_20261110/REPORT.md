# v2.2 결과 보고서 — 선택은 head, 내용은 LLM

브랜치 `jev_v2.2`, 2026-11-10 실행. 계획 원문 `codex/PLAN.md` 개정 6, 실행 기록 `claude/EXEC.md`. 숫자는 모두 결과 파일에서 다시 계산한 값임.

## 0. 요약

**결론: 도구 선택과 청크 선택을 head로 떼어 내고 GRPO로 학습하면, 같은 조건으로 학습한 native A-RAG보다 정확도는 같거나 약간 높고 생성 토큰은 37% 적음. 도구 호출 수는 줄지 않음.**

| 지표 (dev192, greedy) | N0 학습 전 native | N-RL i2 native 학습 | H-RL i2 head 학습 (제안) |
|---|---:|---:|---:|
| EM | 0.146 | 0.120 | **0.162** |
| F1 | 0.193 | 0.174 | **0.202** |
| 생성 토큰 / 문항 | 107.6 | 110.3 | **69.8** |
| 도구 호출 / 문항 | 2.48 | **2.29** | 2.51 |
| greedy 오류 | 0 | 5 | 0 |

- H-RL i2 vs N-RL i2: EM +0.042 [95% 구간 −0.005, +0.089], 생성 토큰 −40.5 [−52.2, −30.4], 도구 호출 +0.22 [+0.14, +0.31].
- 토큰 절감의 대부분(약 33개)은 청크 ID를 LLM이 쓰지 않는 구조에서 나옴. GRPO가 head arm에서 추가로 줄인 것은 약 3개.
- 정확도는 head를 붙이면 먼저 떨어졌다가(0.146 → 0.125) GRPO 2회 후 회복하고 넘어섬(0.162). 구간이 0을 포함하므로 "유지 또는 개선"까지만 주장함.
- 같은 프로세스에서 문항마다 번갈아 잰 지연 시간(학습 전 checkpoint)은 문항당 2.11초 → 1.63초(−23%, 192문항 중 172문항에서 빠름). 학습 후 checkpoint의 통제된 지연 측정은 아직 안 함 (5.9).
- LLM이 청크 ID를 직접 쓸 때 생기는 중복 ID 실패는 read 호출의 0.1~0.4%, 문법이 ID 글자를 바로잡아야 했던 경우는 0~1.6%. head arm은 모든 실행에서 0건 (5.8).
- 사용자 기준(정확도 baseline 이상, 비용 20~50% 감소)에서 생성 토큰은 충족, 도구 호출은 미충족.

## 1. 배경과 목적

- 대상은 A-RAG: LLM이 매 턴 도구 하나를 고르는 검색 에이전트. 도구는 `keyword_search`, `semantic_search`, `read_chunk`, `FINAL` 네 가지.
- 원래 A-RAG에서 LLM은 도구 이름과 청크 ID를 글자로 생성함. 청크 ID는 `c` + 16진수 24자리이며 따옴표 포함 22토큰. dev192 N0에서 생성 토큰 107.6개 중 read 인자의 청크 ID가 27.2개(25%)였음.
- 도구 선택과 청크 선택은 "정해진 후보 중 하나 고르기"이므로 글쓰기가 필요 없음. 이것을 작은 head가 후보에 점수를 매겨 고르게 하면 그 토큰이 0이 됨.
- 두 번째 동기는 생성 실수임. LLM이 선택을 글로 쓰면 문법이 깨지거나, 없는 ID나 이미 읽은 ID를 쓰거나, 같은 ID를 두 번 쓰거나, 도구 이름 철자를 틀릴 수 있음. head는 후보 목록 안의 번호만 고르므로 이런 실수가 구조적으로 불가능함. 실측 비율은 5.8절.
- 이전 실험(v2.1)에서 GRPO만으로 비용을 줄이려 했으나, F1은 조금 올랐고 출력 토큰은 오히려 늘었으며 호출 수는 그대로였음. 그래서 v2.2는 "학습으로 줄이기" 대신 "구조로 줄이기"를 택함.
- 검증할 질문:
  1. head(도구 + 청크)를 붙인 에이전트가 생성 토큰을 줄이면서 정확도를 지키는가.
  2. head arm과 native arm을 같은 GRPO 예산으로 학습했을 때 어느 쪽이 나은가.

## 3. 방법 — 구조

### 3.1 한 턴의 흐름

| 순서 | 무엇을 | 누가 |
|---|---|---|
| 1 | 지금까지의 대화 전체를 LLM에 넣어 hidden state 계산 (prefill) | LLM |
| 2 | 마지막 위치의 hidden state로 도구 4개 중 하나 선택 | **tool head** |
| 3a | `read_chunk`이면 아직 안 읽은 후보 청크 중에서 1~8개 선택 → 코드가 실제 ID로 바꿔 실행 | **chunk pointer** |
| 3b | 검색이면 도구 문법 prefix를 넣고 LLM이 검색어 JSON을 생성 | LLM |
| 3c | `FINAL`이면 LLM이 `{"answer": ..., "support_ids": [...]}`를 생성 | LLM |
| 4 | 도구 결과를 대화에 붙이고 다음 턴 | 코드 |

- head는 LLM의 hidden state만 입력으로 받음. 코퍼스, 정답, 미래 정보에는 접근하지 않음.
- 8회째 호출 뒤에는 `FINAL`이 강제됨. 후보가 없으면 `read_chunk`는 선택 불가.
- `FINAL`의 `support_ids`는 이번 구조에서도 LLM이 ID를 글로 씀 (5.3절 참고).

### 3.2 상태 표현

prefill 결과에서 37개 벡터를 묶음(`pack_hidden`, 각 2560차원). 37개는 마지막 토큰, 질문 끝, 마지막 관측 끝, 마지막 16토큰 평균, 마지막 관측 평균, 그리고 전체를 32구간으로 나눈 평균임.

- tool head는 이 중 **0번(마지막 토큰의 hidden state)만** 사용함.
- 입력은 이전 BC 데이터(2026-10-23 teacher 상태)의 차원별 평균·표준편차로 정규화함 (표준편차 하한 0.1). 이 값은 buffer라 KD와 GRPO에서 바뀌지 않음.
- pointer의 상태 벡터도 같은 마지막 토큰 hidden state임.

### 3.3 Tool head (도구 선택)

MLP 한 층 + 선형 skip 연결.

$$z=(h_{\text{last}}-\mu)/\sigma$$

$$\text{logits}=W_a\tanh(W_1z+b_1)+b_a+W_sz+b_s$$

$$\pi(a\mid s)=\mathrm{softmax}(\text{logits}\ \text{with illegal}\ a\to-10^9)$$

| 구성 요소 | shape | 파라미터 |
|---|---|---:|
| `trunk` $W_1, b_1$ | 2560 → 128, tanh | 327,808 |
| `action` $W_a, b_a$ | 128 → 4 | 516 |
| `skip` $W_s, b_s$ | 2560 → 4 | 10,244 |
| 합계 (학습 대상) | | **338,568** |
| `value`, `success`, `cost` 출력 | 128 → 1, 4, 4 | 1,161 (사용·학습 안 함) |
| 정규화 $\mu, \sigma$ | 2560, 2560 | buffer (고정) |

- 출력: 4개 도구에 대한 확률. 학습 rollout에서는 온도 1로 sampling, 평가에서는 argmax.
- 초기값: 이전 실험의 BC head (`decision_shared_initialization_20261023/head.pt`).
- LLM 4B 대비 약 0.008% 크기.

### 3.4 Chunk pointer (청크 ID 선택)

"후보마다 점수를 매겨 하나씩 고르고, 충분하면 멈추는" 순차 선택기. 상태 쪽과 후보 쪽에 별도 사영(query, key)을 두는 구조라 두 갈래(state 갈래, candidate 갈래)로 이루어짐.

**후보와 후보 표현**

- 후보: 지금까지 검색 결과로 관측됐고 아직 읽지 않은 청크 전부. 실제 K는 1~10개 (teacher 수집 기준).
- 후보 표현: 현재 입력 안에서 그 청크의 검색 결과 객체(제목, 본문 일부)가 차지하는 토큰 구간의 hidden state 평균. 구간은 tokenizer로 정확히 찾고, 못 찾으면 오류로 처리함.

$$c_k=\mathrm{mean}_{t\in\text{span}(k)}h_t$$

**점수**

$$q=W_q\,\mathrm{LN}_s(h_{\text{last}})+b_q+W_{\text{sel}}\,\mathrm{mean}_{j\in S}\mathrm{LN}_c(c_j)$$

$$\text{score}_k=\frac{(W_k\,\mathrm{LN}_c(c_k)+b_k)^\top q}{\sqrt{64}}$$

$$\text{score}_{\text{STOP}}=w_{\text{stop}}^\top\tanh(q)+b_{\text{stop}}$$

- $S$는 이번 read에서 이미 고른 후보 집합. 아무것도 안 골랐으면 $W_{\text{sel}}$ 항은 0.
- 이미 고른 후보의 점수는 $-\infty$, 첫 선택 전에는 STOP도 $-\infty$.
- 확률은 후보 K개 + STOP의 softmax.

**선택 절차**

1. 후보 + STOP 중 하나를 고름 (학습 rollout은 온도 1 sampling, 평가는 argmax).
2. STOP이면 끝. 아니면 $S$에 넣고 1로 돌아감.
3. 8개 또는 후보 전부를 고르면 자동 종료 (이때는 STOP 결정이 없음).
4. 고른 번호를 코드가 실제 청크 ID로 바꿔 `read_chunk`를 실행.

| 구성 요소 | shape | 파라미터 |
|---|---|---:|
| `state_norm` $\mathrm{LN}_s$ | 2560 | 5,120 |
| `candidate_norm` $\mathrm{LN}_c$ | 2560 | 5,120 |
| `query` $W_q, b_q$ | 2560 → 64 | 163,904 |
| `key` $W_k, b_k$ | 2560 → 64 | 163,904 |
| `selected` $W_{\text{sel}}$ | 2560 → 64, bias 없음 | 163,840 |
| `stop` $w_{\text{stop}}, b_{\text{stop}}$ | 64 → 1 | 65 |
| 합계 | | **501,953** |

- 출력: 고른 후보 번호 목록. ID 토큰 생성 0개.
- 구조적으로 잘못된 ID, 중복 ID, 이미 읽은 ID가 나올 수 없음.
- 초기값: 무작위 (seed 20261110).

### 3.5 비교 대상 (native)

- N0 / N-RL은 head 없이 원래 A-RAG 그대로임. LLM이 도구 이름을 허용된 이름들의 토큰 trie 안에서 고르고, 청크 ID도 JSON 문법 안에서 글로 씀 (ID는 관측된 미독 ID로 제한된 enum).
- 공통 계약: 같은 프롬프트, 같은 문법 제약, 같은 답 길이 상한, 같은 미독 후보 규칙.

### 3.6 조건 이름

| 이름 | 구조 | 학습 |
|---|---|---|
| N0 | native | 없음 |
| N-RL i1, i2 | native | GRPO 1회, 2회 |
| H0-G | tool head, 청크 ID는 LLM이 생성 | KD만 (진단용) |
| H0-P | tool head + chunk pointer | KD만 |
| H-RL i1, i2 | tool head + chunk pointer | KD 후 GRPO 1회, 2회 |

## 4. 방법 — 학습

### 4.1 1단계: teacher 수집과 KD (LLM 고정)

- teacher: N0를 train 576문항에 greedy로 실행. 결정 상태 2,065개, 유효 read 상태 358개.
- 라벨:
  - 도구: teacher가 고른 도구.
  - 청크: 후보 중 정답 근거 문단이 있으면 그 문단들 (최대 8개, 후보 순서) — 296상태. 없으면 teacher가 고른 청크 — 62상태. 오류 1상태 제외.
  - 순수 KD가 아니라 "teacher KD + 정답 근거 지도"임. 정답 근거는 학습 라벨에만 쓰고 추론 입력에는 없음.
- 손실: 질문 균형 도구 CE(label smoothing 0.05) + 질문 균형 pointer 순차 CE, 가중치 1:1.
- AdamW lr 3e-4, 최대 100 epoch, 내부검증 CE 최소 checkpoint 선택 → epoch 14 (검증 CE 1.239, 도구 teacher 일치율 93.1%).
- pointer 품질 gate (내부검증 정답 근거가 있는 66상태의 support F1이 teacher 이상): pointer 0.698, teacher 0.714로 **미달**. 차이 −0.016 (66상태 중 약 1개), 구간 [−0.110, +0.078]. 사용자 지시로 진행함.
- 원인 분석: 첫 선택이 정답 근거인 비율은 pointer 50/66, teacher 51/66로 같음. pointer가 평균 1.03개만 고르고 멈춤 (teacher 1.68개, 정답 근거 1.26개).

### 4.2 2단계: GRPO (LLM 전체 + head 전체 학습)

**rollout**

- 문항당 8회, 온도 1 (도구 선택, pointer, LLM 생성 모두).
- iteration $k$의 rollout은 iteration $k-1$의 정책으로 수집함 (on-policy, 1 pass).

**보상**

$$Q=0.8\,\mathrm{EM}+0.2\,\mathrm{F1}$$

$$C_{\text{tok}}=0.10\,Q\,\frac{T}{T+128}$$

$$C_{\text{call}}=0.15\,\mathrm{EM}\,\frac{N}{8}$$

$$R=Q-C_{\text{tok}}-C_{\text{call}}$$

- $T$는 에피소드 전체 생성 토큰, $N$은 도구 호출 수. 오류나 빈 답은 EM = F1 = 0이므로 $R=0$.
- 비용 항은 정답이거나 부분 정답일 때만 작동함. 그래서 오답은 아무리 짧아도 정답보다 보상이 높을 수 없음 (정답 최소 0.75, 오답 최대 0.2).

**단계 보상 (S3 pilot 결과로 채택)**

$$r_t=0.05\,\frac{|\text{처음 검색된 정답 근거}_t|}{|G|}\quad(\text{검색 단계})$$

$$r_t=0.05\,\frac{|\text{처음 읽은 정답 근거}_t|}{|G|}\quad(\text{read 단계})$$

마지막 단계에 $R$을 더함. 에피소드당 단계 보상 합은 0.10 이하. $G$는 정답 근거 집합이며 학습 보상에만 쓰임.

**advantage (같은 문항 8회끼리 비교)**

$$G_{i,t}=\sum_{s\ge t}r_{i,s}$$

$$A_{i,t}=G_{i,t}-\frac{1}{7}\sum_{j\ne i}G_{j,t}$$

- 이미 끝난 rollout의 $G_{j,t}$는 0. 표준편차로 나누지 않음.
- 같은 단계의 모든 결정(도구 선택, pointer 선택, LLM 토큰)에 같은 $A_{i,t}$를 줌.

**손실**

$$\rho=\exp(\log\pi_\theta-\log\pi_{\text{old}})$$

$$\ell=-\min(\rho A,\ \mathrm{clip}(\rho,0.8,1.2)A)+0.02\,k_3$$

$$k_3=e^{\log\pi_{\text{ref}}-\log\pi_\theta}-(\log\pi_{\text{ref}}-\log\pi_\theta)-1$$

$$L=\frac{1}{16}\sum_{\text{batch 16 궤적}}\sum_t\sum_{e\in t}\ell_e$$

| arm | 손실에 들어가는 결정 $e$ |
|---|---|
| head | 도구 선택 1개 (강제 FINAL 제외), pointer 선택 각각과 STOP, LLM이 쓴 검색어·최종 답 토큰 |
| native | 도구 이름 분기 토큰의 합 1개, LLM이 쓴 인자·청크 ID·최종 답 토큰 |

- 문법상 강제된 토큰은 손실에서 제외. 길이 정규화 없음.
- $\pi_{\text{ref}}$는 각 arm의 iteration 0 정책 (head arm은 KD head + 원본 LLM).

**gradient가 LLM까지 흐르는 방식 (replay)**

- 업데이트 때 rollout에서 저장한 feature를 쓰지 않고, 같은 토큰열을 현재 LLM에 다시 넣어 hidden state와 후보 표현을 새로 계산함.
- 그래서 도구 선택과 청크 선택의 손실이 head를 거쳐 LLM 전체로 전달됨. head arm 업데이트마다 LLM, trunk, action, skip, pointer 다섯 경로 모두에 gradient가 있는 것을 확인함.

**최적화**

| 항목 | 값 |
|---|---|
| LLM | 전체 파라미터 학습, FP32 master 가중치 + FP32 AdamW, lr 1e-6. 추론용 BF16은 반올림 사본 |
| head | tool head의 trunk·action·skip과 pointer 전체, AdamW lr 5e-5 |
| batch | 16 궤적, iteration당 1 pass. advantage가 0이 아닌 궤적만 사용 (iteration당 head 1,432~1,448개, native 1,262~1,418개 / 1,536개) |
| gradient clip | norm 1 |
| iteration | 2회. 주 판정은 iteration 2 (사전 고정) |
| 메모리 | 업데이트 최대 70.6GB, rollout 약 11GB |

### 5.6 정성평가

- **도구 순서**: H0-P는 "키워드 검색 → 의미 검색 → (read) → 답" 한 패턴에 쏠렸음 (KSRF 105, KSF 59 / 192). H-RL i2는 의미 검색으로 시작하는 경우가 늘어남 (KSRF 79, KSF 31, SSF 26, SRF 26). N0가 원래 의미 검색으로 시작하던 문항들과 같은 방향임.
- **빈 답 증가**: H-RL i2의 빈 답이 81 → 92로 늘어남. H0-P에서 틀린 답을 쓰던 21문항이 빈 답으로 바뀜. 프롬프트가 "근거가 부족하면 빈 답"을 지시하므로 오답 대신 답을 보류하는 쪽으로 움직였을 가능성이 있음 (검증 안 함). 학습 rollout(온도 1)에서는 빈 답이 줄었던 것과 반대임.
- **정답 전환 사례**:
  - 표기 회복: "1 January 1973" → "1973".
  - 다른 근거 경로: "university" → "hogeschool" (의미 검색 2회 후 read).
- **pointer**: 학습 후에도 read 한 번에 1.02개만 고름. 다만 읽은 근거 재현율은 .130 → .158로 오름. "몇 개를 읽을지"보다 "무엇을 검색하고 무엇을 읽을지"가 좋아진 것으로 보임.
- **공통 한계**: 2~4hop 질문인데 평균 2.5회만 호출하고 질문 전체를 한 번에 검색함. 모델은 호출이 많은 것이 아니라 근거를 덜 모으는 상태임. 호출 수 감소 목표가 달성되지 않은 배경으로 봄.

**native(N-RL i2)는 틀리고 H-RL i2는 맞힌 문항**

14문항 (반대는 6문항). 그중 8문항은 학습 전 N0도 틀렸음. 대표 사례 (K = keyword_search, S = semantic_search, R = read_chunk, 괄호는 그 호출로 얻은 정답 근거 수):

| 문항 (정답) | N-RL i2 | H-RL i2 | 바뀐 점 |
|---|---|---|---|
| Seventh Brings Return 공연자의 결성 연도 (1985) | K("Seventh Brings Return", "Syd Barrett", "form")(1/2) → R 1개 → "2006" | S("formation year of the band Seventh Brings Return …")(1/2) → **S("when was the band Violeta de Outono formed")**(1/2) → "1985" | 1단계에서 찾은 밴드 이름으로 2단계를 다시 검색 |
| 첫 서쪽 항해로 아시아에 간 탐험대장의 아버지 (Estêvão da Gama) | K(…)(0/4) → S(…)(2/4) → R 4개 → 빈 답 | S(…)(2/4) → **S("who fathered Vasco da Gama")**(1/4) → "Estêvão da Gama" | 중간 개체(Vasco da Gama)를 이름으로 검색. 호출 3 → 2, 생성 토큰 173 → 91 |
| 같은 체인의 다른 질문 (Estêvão da Gama) | S(…)(0/4) → R 1개(0) → "Portuguese" | S(…)(1/4) → **S("father of Vasco da Gama")**(1/4) → "Estêvão da Gama" | 위와 같은 패턴 |
| 목성의 중력을 이용한 우주선 (Voyager probes) | K(…)(1/2) → S(…)(1/2) → R 3개(근거 1) → "Voyager 1" | S(…)(1/2) → R 1개(근거 1) → "Voyager probes" | 비근거 청크를 섞어 읽지 않음. 호출 3 → 2, 생성 토큰 208 → 56 |
| George IV의 사망 장소 (Windsor Castle) | K(…)(1/3) → R 3개 → "Buckingham Palace" | K(…)(1/3) → S("place of death of George IV")(0/3) → R 1개 → "Windsor Castle" | 질문의 마지막 hop을 따로 검색. 생성 토큰 140 → 71 |
| Virginia 수도 이전 연도 (1779) | K(…)(1/4) → `"top_k": 5000…` 폭주로 잘림 | S(…)(3/4) → R 1개 → "1779" | native의 생성 오류 (6.3) |
| Chopin 관련 국가의 흡연 금지 시작일 (29 March 2004) | 검색 없이 바로 빈 답 | S(…)(1/4) → R 1개 → "29 March 2004" | native는 도구를 쓰지 않고 포기 |
| 영국의 EC 가입 연도 (1973) | … → R 2개 → "1 January 1973" | … → R 1개 → "1973" | 답 표기만 다름 (EM 기준) |

- 가장 많이 보이는 변화는 **다음 hop의 개체를 이름으로 다시 검색하는 것**임. 두 번째 이후 검색어에 질문에 없는 고유명사가 들어간 에피소드 비율 (대문자 단어 기준의 간이 측정):

| 조건 | 새 개체를 검색한 에피소드 | 그 안의 EM | 나머지의 EM |
|---|---:|---:|---:|
| N0 | 60/192 (31%) | 7/60 | 21/132 |
| N-RL i2 | 44/192 (23%) | 7/44 | 16/148 |
| H0-P | 60/192 (31%) | 11/60 | 13/132 |
| H-RL i2 | **82/192 (43%)** | 16/82 | 15/110 |

- H-RL은 학습 후 이 행동이 늘었고 (31% → 43%), N-RL은 줄었음 (31% → 23%). N-RL은 대신 호출 수를 줄이는 쪽으로 움직였음.
- read는 H-RL이 1개씩만 읽어 비근거 청크를 섞는 경우가 적음. 반대로 근거를 2개 이상 읽어야 하는 문항에서는 불리할 수 있음.

### 5.8 LLM이 직접 쓸 때의 형식·ID 오류

native는 도구 이름을 허용된 이름 trie 안에서, 청크 ID를 "관측된 미독 ID" enum 문법 안에서 생성함. 그래서 철자가 틀린 도구 이름이나 없는 ID는 문법이 막음. 남는 실수와 문법이 막아 준 실수를 셈.

| 실행 | read 호출 | 중복 ID로 에피소드 실패 | 문법이 ID 글자를 바로잡음 |
|---|---:|---:|---:|
| teacher N0 (train 576, greedy) | 359 | 1 (0.28%) | 4 (1.1%) |
| N0 dev192 (greedy) | 115 | 0 | 1 (0.9%) |
| H0-G dev192 (tool head, ID는 LLM) | 123 | 0 | 2 (1.6%) |
| N-RL i1 / i2 dev192 | 123 / 105 | 0 / 0 | 0 / 0 |
| native 학습 rollout 1 / 2 (온도 1) | 905 / 935 | 4 (0.44%) / 1 (0.11%) | 미측정 |
| **head arm 전체 (H0-P, H-RL i1·i2, 학습 rollout 2회)** | **pointer** | **0** | **해당 없음** |

- **중복 ID**: 문법 라이브러리가 `uniqueItems`를 강제하지 않아 LLM이 같은 ID를 두 번 쓰면 생성 후 검증에서 실패하고, 그 문항은 오류로 끝남 (예: `['c58f…', 'c60a…', 'c58f…']`).
- **문법이 바로잡은 경우**: LLM이 원래 쓰려던 다음 글자가 허용된 어떤 ID와도 맞지 않아 문법이 다른 글자로 바꾼 경우. 문법 없이 생성했다면 없는 ID가 됐을 경우임.
- **도구 이름**: 두 arm 모두 철자 실수가 구조적으로 불가능함. 문법 없이 자유 생성할 때의 비율은 측정하지 않음.
- **pointer는 이 두 종류의 실수가 모두 0이고, ID용 문법 장치 자체가 필요 없음.** 남은 생성 오류는 두 arm 공통인 `top_k` 숫자 폭주 (6.3)뿐임.
- 최종 답의 `support_ids`는 head arm에서도 LLM이 ID를 씀. 이 부분의 오류는 별도로 세지 않았음.

### 5.9 지연 시간

**측정 가능했던 것: 학습 전 checkpoint, 같은 조건의 교대 실행**

S2 dev192 평가는 한 프로세스에서 문항마다 N0 → H0-P 순서로 번갈아 실행했음 (05:41~05:53 UTC, GPU에는 이 작업만 있었음, HF transformers batch 1). 같은 base LLM이라 구조 차이만 비교됨.

| 조건 | 문항당 시간 (평균 / 중앙값) | prefill 합 | 도구 실행 | 생성 토큰 |
|---|---:|---:|---:|---:|
| N0 | 2.11 / 2.01초 | 0.18초 | 0.37초 | 107.6 |
| H0-G (06:00 UTC 별도 실행, 단독) | 2.08 / 1.97초 | 0.18초 | 0.39초 | 105.9 |
| H0-P | **1.63 / 1.61초** | 0.18초 | 0.39초 | 72.9 |

- H0-P − N0: **−0.48초 [−0.57, −0.40], −23%**. 192문항 중 172문항에서 빠름.
- tool head만 붙인 H0-G는 N0와 거의 같음. 지연 감소는 pointer(청크 ID를 쓰지 않는 것)에서 옴. 줄어든 생성 토큰 1개당 약 14ms.
- pointer 자체의 계산 시간은 문항당 약 1ms.

**아직 측정하지 못한 것: 학습 후 checkpoint (H-RL i2 vs N-RL i2)**

- dev192 평가 때 head arm은 native 업데이트와 GPU를 나눠 썼고 native arm은 단독으로 돌았으므로, 그 기록의 시간은 비교할 수 없음.
- 통제된 측정용 스크립트 `scripts/bench_v22_latency.sh`를 준비함. dev 문항 hop별 16개(48문항)를 head, native, native, head 순서로 돌려 기계 상태의 변화가 두 arm에 똑같이 걸리게 하고, 문항 단위 차이와 구간을 계산함. GPU에 다른 작업이 있으면 시작하지 않음. 예상 소요 약 10분.
- vLLM: 이 구조는 생성 도중 hidden state를 꺼내 head를 실행해야 해서 vLLM에 바로 올릴 수 없음. 이번에는 시도하지 않음. vLLM처럼 토큰당 시간이 짧은 환경에서는 절감되는 초 단위 시간도 그만큼 작아짐 (미측정).

## 6. 진행 중 문제와 계획 변경

### 6.1 gate 실패와 사용자 결정

| 시점 | gate | 측정 | 처리 |
|---|---|---|---|
| S1 | pointer support F1 ≥ teacher | .698 < .714 | 사용자 지시로 진행. FAIL 기록 유지 |
| S3 | 호출 절감 직접 비교 그룹 ≥ 10% | head 2/24 (8.3%) | 사용자 확인 후 진행 |
| S4 smoke | replay 단위 최대 오차 ≤ 0.05 | 최대 0.898 | 사용자 결정으로 "평균 오차 ≤ 0.05"로 재정의 (6.2) |

### 6.2 BF16 replay 차이

- rollout은 KV 캐시로 한 토큰씩 계산하고, 업데이트는 전체 토큰열을 한 번에 다시 계산함.
- FP32에서는 두 방식이 0.001 이내로 일치함. BF16에서는 대부분 같다가 드물게 한 토큰에서 크게 갈림 (최대 11.4 nat).
- 평균 오차는 0.005~0.009이고 PPO clip 범위 밖 단위는 약 1%. 이전 v2.1의 "replay gap"(평균, 0.008~0.031)과 같은 정의로 gate를 재정의함.

### 6.3 `top_k` 숫자 폭주

- 검색 인자 `"top_k": 5` 뒤에 숫자를 하나 더 뽑으면 0을 생성 한도까지 반복함.
- 원인: 도구 정의는 `top_k`를 정수 1~20으로 정하지만, 문법 강제 라이브러리(lm-format-enforcer 0.11.3)가 정수 범위를 무시함.
- 영향: 학습 rollout에서 0.07% → 0.49% (검색 호출당)로 늘었고, N-RL i2의 greedy 평가에서 5건(2.6%) 발생함. H-RL은 greedy에서 0건.
- 수정: 커밋 `5486893`에서 범위가 있는 정수 인자에 허용값 enum을 붙임. 이번 실행은 고정 스냅샷이라 수정 전 조건으로 돌았음.

### 6.4 인프라

- native 업데이트 1이 저장 직전 디스크 부족으로 실패해 다시 돌림 (약 45분 손실). 다른 프로젝트로 모델 16GB가 복사된 것이 원인.
- iteration 2의 optimizer 상태는 디스크 때문에 저장하지 않음. 이어서 학습하려면 iteration 2부터 다시 해야 함.
- 다른 프로젝트의 CPU 작업 때문에 rollout이 일시적으로 3배 느려짐. 결과 수치에는 영향 없음.
- head dev 평가는 native 업데이트와 겹쳐, native dev 평가는 단독으로 돌았음. 그래서 wall-clock은 arm끼리 비교하지 않음.

## 7. 한계

- seed 1개. dev192는 이전 실험부터 여러 번 본 개발 셋. test320은 평가하지 않음.
- 정확도 차이는 대부분 구간이 0을 포함함. 우월성이나 비열등성(허용 margin 미합의)을 주장하지 않음.
- tool head와 pointer를 따로 학습한 조건이 없어 GRPO 후 각 head의 기여를 분리할 수 없음.
- 보상 항별 ablation 없음.
- head arm만 KD 비용(teacher 수집 약 26분 + KD)이 추가로 들었음.
- 지연 시간은 학습 전 checkpoint의 교대 실행(5.9)만 통제된 측정임. 학습 후 checkpoint의 지연은 주장하지 않음.
- 5.6의 "새 개체 검색" 비율은 대문자 단어 기준의 간이 측정임.

## 8. 다음 단계 제안

1. **support_ids도 pointer로**: 최종 답의 support_ids(문항당 약 20토큰)도 청크 ID 목록임. 같은 pointer로 바꾸면 생성 토큰을 약 50개 수준까지 더 줄일 수 있음.
2. **호출 수를 줄이려면 다른 지점이 필요함**: 이번 데이터에서 모델은 호출이 많은 상태가 아님. 호출 감소는 도구 호출이 더 많고 경우의 수가 큰 환경(예: AtomMem의 chunk별 메모리 연산)에서 시험하는 것이 맞아 보임.
3. **test320 평가**: 주 checkpoint(H-RL i2, N-RL i2)를 한 번 평가해 dev 결과가 유지되는지 확인. 두 arm 합쳐 약 15분.
4. **학습 후 지연 측정**: GPU가 비었을 때 `bash scripts/bench_v22_latency.sh` (약 10분).
5. **seed 반복**: 정확도 차이를 확정하려면 seed 2~3개 반복이 필요함.
